## 2. 사용자가 직접 확정한 계약

아래는 제안이 아니라 사용자 직접 발언으로 확정된 내용이다.

### 2.1 위치와 조작

1. 절도는 별도 전체화면이나 별도 침입 화면이 아니라 메인 화면의 중앙 리소스 필드에서 일어난다.
2. 플레이어는 자신이 원할 때 절도한다.
3. 중앙 필드는 그리드다.
4. 그리드에는 작은 리소스 조각이 있다.
5. 플레이어는 방향키로 직접 움직인다.
6. 플레이어가 리소스 조각을 직접 훔친다.
7. 핵심 문제는 플레이어가 컨트롤한다는 느낌과 재미가 부족하다는 점이다.

### 2.2 위험의 성장과 감사

1. 처음에는 장애물과 레이더 또는 감시가 없다.
2. 시간이 지나면서 그리드 곳곳에 벽이 생긴다.
3. 특정 영역에는 감시 전에 암시 또는 신호가 먼저 온다.
4. 그 뒤 해당 영역에서 실시간 부분 감시가 이루어진다.
5. 감시는 플레이어가 특정 리소스 수량을 보유했는지 검사하는 방식이 아니다.
6. 플레이어는 자신의 절도 동작이 적발되지 않도록 해야 한다.

### 2.3 경제와 정보

1. 확보 리소스에는 칸과 하드 상한이 없다.
2. 추론·기억·유창성은 하나의 확보 공간에 함께 존재하지만 각 토큰의 분야와 안정 ID를 유지한다.
3. 해킹 해금은 단일 RES 총량이 아니라 분야별 정확한 비용 벡터를 요구한다.
4. 현재 행동 가능한 항목의 요구만 공개하며 이후 요구 조합은 숨긴다.
5. 균등하게 훔쳐도 실제 요구 조합이 불균형할 수 있어 과잉 전용과 추가 절도의 압력이 생긴다.
6. 많이 비축하는 대가는 저장 한도가 아니라 절도 때 이미 발생한 회사 성능 손실·의심·감사 위험이다.

### 2.4 화면 제작 원칙

1. 공간을 먼저 계산하고 플레이 영역을 우선한다.
2. 튜토리얼에서 한 번 설명할 내용을 아이콘·패널마다 반복하지 않는다.
3. 행동, 현재 위험, 실제 결과를 전달하지 않는 텍스트는 상시 화면에 넣지 않는다.
4. 코드 수정량, 문서 생성량, 테스트 개수는 재미와 사용성의 성과로 취급하지 않는다.
5. 사용자 목업과 직접 확정한 아이디어는 장식 참고가 아니라 구현 계약으로 취급한다.

## 3. 명시적으로 철회하거나 금지하는 해석

다음 해석은 폐기한다.

1. 전용 전체화면 침입 모드를 권장한 이전 제안은 철회한다.
2. 중앙 필드와 별도 침입 화면에 같은 회사 리소스를 중복 표현하지 않는다.
3. 입장·퇴장·반출 같은 전환을 사용자 확정 없이 추가하지 않는다.
4. 그리드를 다른 화면의 별도 미니게임으로 만들지 않는다.
5. 이동만으로 자동 절도된다고 아직 확정하지 않는다.
6. 출구로 돌아와야 확보된다고 아직 확정하지 않는다.
7. 적발 시 압수·강제 퇴장·즉시 패배·정확한 의심 증가량을 임의로 정하지 않는다.
8. 기존 성공 절도의 의심 +2.4를 적발 처벌 수치라고 재해석하지 않는다.
9. 벽 생성 시점, 감사 지속시간, 신호 시간, 이동 간격을 근거 없이 숫자로 고정하지 않는다.
10. 해킹 네트워크 UI 2안이 새 자원 절도 조작의 승인된 기반이라고 간주하지 않는다.

전용 전체화면 제안이 성립하지 않는 이유는 명확하다. 리소스 위치의 이중 정본, 화면 전환, 시간·감사 동기화, 입장·퇴장 상태, 저장·리플레이 경계가 새로 생기고, 사용자가 요구한 메인 필드의 즉시 절도를 훼손한다. 다음 담당자는 이 제안을 되살리지 않는다.

## 5. 감사와 조작이 실제로 굴러가는 권장안

이 절은 다음 담당자가 검토해 사용자에게 제시할 하나의 완결된 권장안이다. 아직 사용자 승인이 아니다.

### 5.1 평상시

1. 중앙 리소스 필드는 항상 같은 그리드다. 화면 전환은 없다.
2. 플레이어 표식은 그리드 안에 있고, 중앙 필드가 키보드 포커스를 가지면 방향키가 표식을 한 칸씩 움직인다.
3. 포커스는 입력 소유권일 뿐 별도 게임 모드나 전체화면이 아니다.
4. 이동과 절도를 분리한다. 리소스 칸에 도착해도 자동으로 훔치지 않고, 별도 확정 입력을 했을 때만 절도 동작이 시작된다.
5. 이 분리가 필요한 이유는 플레이어가 원하는 순간을 선택하게 하고, 감시가 위치가 아니라 절도 동작을 판정하게 하기 위해서다.
6. 성공 절도는 기존 BEGIN_BLOCK_SEPARATION → DIVERT_BLOCK_TO_RESERVE 의미를 재사용해 동일 토큰 ID·분야·성능 손실·의심을 보존한다.

별도 절도 키와 절도 동작의 길이는 미확정이다. 단일 즉시 입력이면 감시가 단순한 금지등이 되어 긴장감이 약해질 가능성이 크다. 권장 비교안은 짧고 취소 가능한 절도 동작이며, 신호가 활성 감시로 바뀌기 전에 취소하거나 이동할 수 있어야 한다. 길이는 실제 이동 간격과 반응 테스트로 정하며 임의 숫자로 확정하지 않는다.

### 5.2 공식 감사가 시작될 때

1. 월말 공식 감사가 시작되어도 새 화면이나 모달로 이동하지 않는다.
2. 같은 중앙 그리드에 감사 상태가 겹친다.
3. 감사 대상·기존 성능 판정·새 부분 감시가 어떻게 결합되는지는 8절의 최우선 미결정 사항이다.
4. 권장 시간 모델은 기존 blocking audit의 캘린더 정지 의미를 보존하되, 제출 모달 대신 중앙 필드의 결정론적 실시간 감사 타임라인을 실행하는 것이다.
5. 감사 시작 시 이전 0/1/2/4배속을 저장하고 서비스 캘린더 진행을 멈춘다.
6. 감사 타임라인 자체는 고정된 1배속 실시간으로 진행한다. 사용자가 설정을 열거나 앱이 비활성화되면 공정성을 위해 타임라인과 조작을 함께 멈춘다.
7. 감사 종료 또는 판정 후 이전 서비스 속도를 복원한다.

이 모델을 권장하는 이유:

- 2배속·4배속에서 방향키 조작과 반응 시간을 왜곡하지 않는다.
- 감사 중 여러 서비스 날짜와 주간·월간 사건이 동시에 진행되는 충돌을 피한다.
- 현재 blocking audit의 큰 저장·리플레이 의미를 덜 훼손한다.
- 별도 화면 없이 메인 필드에서만 조작한다.

단, 사용자가 캘린더가 계속 흐르는 감사를 원한다면 이 권장안은 폐기하고 기간·배속·일일 사건 충돌을 다시 설계해야 한다.

### 5.3 한 번의 감시 파동

한 파동은 다음 순서다.

1. 무감시 또는 해제 상태
2. 특정 부분 영역에 사전 신호
3. 반응 가능 시간
4. 같은 영역의 활성 감시
5. 감시 해제
6. 다음 영역의 사전 신호

판정 규칙:

- 활성 감시 영역 안에 플레이어가 서 있거나 지나가는 것만으로는 적발되지 않는다.
- 활성 감시 영역에서 절도 동작을 시작하거나 절도 확정 구간이 겹칠 때 적발된다.
- 보유량, 특정 분야 수량, 비축 총량을 스캔하지 않는다.
- 경고 영역에서는 절도를 취소하고 이동할 수 있다.
- 플레이어는 경고를 보고 안전 영역으로 이동해 다른 자원을 노리거나, 해당 파동이 끝날 때까지 기다릴 수 있다.

따라서 피한다는 말은 단순히 빨간 칸에서 손을 떼는 것만을 뜻하지 않는다. 벽 때문에 경로가 달라지는 그리드에서 다음 안전 영역과 노릴 자원까지 이동 시간을 계산해 위치를 바꾸는 것이다.

### 5.4 벽

권장 해석은 벽을 캠페인 진행·보안 강화에 따라 누적되는 지속 지형으로 두고, 감사 중 실시간으로 변하는 것은 감시 영역으로 제한하는 것이다.

이유:

- 예고 없이 벽이 솟아 플레이어를 가두는 불공정을 피한다.
- 플레이어가 반복 플레이로 공간을 학습할 수 있다.
- 장기 압박은 경로가 좁아지는 것으로, 단기 압박은 감시 파동으로 역할이 나뉜다.
- 경로 계산과 저장·리플레이가 단순해진다.

사용자가 감사 도중에도 벽이 생성되길 원한다면 최소한 사전 신호, 플레이어 칸 보호, 유일한 경로 보호, 생성 후 BFS 검증이 필요하다.

### 5.5 적발

확정 가능한 최소 의미:

1. 활성 감시와 겹친 절도는 성공 절도로 처리하지 않는다.
2. 성공한 DIVERT_BLOCK_TO_RESERVE 명령을 기록하지 않는다.
3. 같은 위치에서 즉시 읽히는 국소 피드백을 낸다.

아직 정하면 안 되는 것:

- 의심 증가량
- 토큰 압수
- 강제 이동 또는 감사 종료
- 회사 성능 추가 손실
- 감사 최종 실패와의 연결

이 처벌은 경제 밸런스와 저장·리플레이에 영향을 주므로 사용자 승인 없이 구현 정본에 넣지 않는다.

## 6. 공간·시간을 연산해야 하는 최소 규칙

다음 담당자는 감으로 칸과 시간을 정하지 않는다.

### 6.1 공간

1. 지원 뷰포트 1280×720과 1440×900에서 실제 중앙 필드의 가용 픽셀을 측정한다.
2. 상단 제어줄, 좌우 패널, 하단 지표를 제외한 뒤 행·열·셀 크기 후보를 계산한다.
3. 플레이어, 세 분야 조각, 벽, 경고, 활성 감시가 장식 없이 동시에 구분되는 최소 셀 크기를 실제 캡처로 확인한다.
4. 기능 없는 설명 패널이나 로그가 그리드를 줄이면 삭제한다.
5. 사용자가 제공한 목업과 비교할 때 같은 뷰포트에서 큰 비례·중앙 점유·경계 위치를 수치로 기록한다.

### 6.2 경로

매 지형 후보마다 BFS 또는 동등한 검사를 실행한다.

- 플레이어에서 모든 현재 리소스까지 도달 가능한가
- 최소 하나의 안전 칸까지 도달 가능한가
- 벽이 유일한 통로를 닫지 않는가
- 플레이어 칸에 벽이 생기지 않는가
- 경고 뒤 활성화 전에 안전 영역으로 갈 수 있는가
- 두 감시 영역이 겹쳐도 전체 연결 성분을 봉쇄하지 않는가

필수 부등식:

경고 시간 ≥ 현재 위치에서 가장 가까운 안전 칸까지 필요한 이동 시간 + 진행 중 절도 취소 시간 + 입력 여유

이 부등식을 만족하지 못한 파동은 생성하지 않는다.

### 6.3 시간

다음 값을 먼저 가정하고 실제 플레이 뒤 기록한다.

- 한 칸 이동 간격
- 키 반복 처리 간격
- 절도 시작·취소·확정 시간
- 신호 선행 시간
- 활성 감시 시간
- 파동 사이 해제 시간
- 감사 전체 시간
- 첫 조각과 여러 조각을 훔치는 데 걸린 시간

숫자는 코드에 먼저 박아 넣고 합리화하지 않는다. 목표 경험, 최단 경로, 인간 반응 시간, 실제 브라우저 조작 결과에서 역산한다.

### 6.4 결정론과 저장

제품 통합본의 벽, 파동, 커서 위치, 진행 중 절도, 남은 감사 시간은 저장·새로고침·리플레이 뒤 같은 의미를 가져야 한다. 이 상태가 플레이 결과에 영향을 준다면 save v8와 command v4에 몰래 필드를 추가하지 않는다. 새 명령·저장 버전 또는 기존 버전의 명시적 호환 판정이 필요하다.

첫 회색 상자는 승인 전이므로 비영속 프로토타입 상태를 사용할 수 있다. 이 경우 다음을 명확히 보고한다.

- 저장·새로고침 재개가 아직 지원되지 않음
- 제품 명령 로그의 정본이 아님
- 사용자 조종감 확인 뒤 버전 설계를 별도 진행함

## 7. 첫 프로토타입의 정확한 범위

첫 프로토타입은 실제 메인 화면 중앙 필드에서 보이게 만든다. 별도 샌드박스 페이지만 보여 주고 공간 문제가 해결됐다고 주장하지 않는다.

포함:

1. 제한색 회색 상자 그리드
2. 플레이어 표식
3. 추론·기억·유창성 조각
4. 방향키 이동
5. 별도 절도 입력 후보
6. 초반 무장애·무감시 상태
7. 최소 한 단계의 벽 증가 상태
8. 신호 → 활성 부분 감시 → 해제 파동
9. 감시 중 절도 판정
10. BFS 도달 가능성과 안전 창 검사
11. 사용자가 바로 조작할 로컬 실행 주소

제외:

- 최종 미술
- beam, glass, shader, grain 같은 장식 효과
- 전체 앱 재디자인
- 해킹 트리의 추가 시각 개편
- 적발 처벌의 임의 확정
- 제품 저장·명령 버전 변경
- 중단된 UI 2안 WIP 병합

첫 화면에 허용되는 상시 텍스트는 현재 행동, 현재 위험, 실제 결과에 필요한 최소량뿐이다. 조작 설명은 최초 튜토리얼 또는 접근성 경로로 옮긴다.

## 8. 다음 담당자가 먼저 닫아야 할 미결정 사항

가장 먼저 해결할 질문은 하나다.

새 실시간 부분 감시가 현재의 공식 감사 위장·제출 상호작용을 대체하는가, 아니면 감사 중 절도 감시로 추가되고 기존 성능 판정·위장 제출도 남는가?

권장안은 다음과 같다.

- 기존 별도 감사 제출 모달은 제거한다.
- 월초 감사 추첨과 대상 분야, 월말 발생, 최종 성능 판정은 보존한다.
- 월말에는 같은 중앙 필드에서 실시간 부분 감시가 진행된다.
- 감사 종료 시 대상 분야 성능을 판정한다.
- 다른 분야 토큰을 빈 칸에 옮겨 위장하는 기존 퍼즐은 새 그리드의 공간·절도 루프와 충돌하므로 그대로 병존시키지 않는다.

이 권장안은 기존 감사 UI를 제거하는 제품 규칙 변경이므로 사용자 승인 전에는 구현 정본으로 확정하지 않는다.

그 다음 순서의 미결정 사항:

1. 벽이 캠페인 진행에 따라 지속되는지, 감사 도중에도 변하는지
2. 절도 입력이 즉시인지 짧은 유지 동작인지
3. 적발 처벌
4. 감사 전체 시간과 파동 수
5. 감사 중 서비스 캘린더 정지 여부
6. 그리드 상태의 저장·명령 버전

여러 질문을 한꺼번에 사용자에게 떠넘기지 않는다. 완결된 권장안을 제시하고 결과를 설명한 뒤 가장 큰 분기 하나만 확인한다.

## 9. 실행 순서

### 단계 A — 인수 확인과 설계 승인

1. 이 문서를 끝까지 읽는다.
2. P0 경제 명세와 구현 계획을 읽는다.
3. 4.2절의 관련 코드를 직접 확인한다.
4. 사용자 확정, 저장소 사실, 권장안을 세 목록으로 분리해 첫 업데이트에 적는다.
5. 5절의 흐름이 실제로 성립하는지 스스로 반례를 찾는다.
6. 8절의 첫 질문에 대한 권장안을 사용자에게 제시하고 승인받는다.

### 단계 B — 회색 상자

1. P0 인계 커밋에서 분기한 독립 브랜치에서만 작업한다.
2. ResourceBoard의 실제 중앙 공간을 측정한다.
3. 그리드·플레이어·세 분야 조각·이동만 먼저 구현한다.
4. 실제 브라우저에서 조작하고 공간과 이동 간격을 기록한다.
5. 성공 절도를 기존 P0 명령에 연결한다.
6. 벽과 신호·부분 감시를 추가한다.
7. BFS와 시간 부등식 검사를 추가한다.
8. 같은 두 뷰포트에서 직접 조작하고 캡처한다.

### 단계 C — 사용자 플레이

1. 실행 주소와 정확한 조작을 짧게 전달한다.
2. 사용자가 플레이할 수 있도록 서버를 유지한다.
3. 재미·압박감·상용 품질을 자체 승인하지 않는다.
4. 사용자 피드백 전에는 최종 미술과 전체 회귀로 범위를 넓히지 않는다.

### 단계 D — 승인 뒤 제품 통합

1. 감사 규칙과 적발 처벌을 정본 명세에 반영한다.
2. 저장·명령 버전 경계를 판정한다.
3. 테스트 우선으로 결정론·리플레이·저장 이관을 구현한다.
4. 관련 단위·브라우저 검증을 통과한 뒤 전체 기준선을 재검증한다.
