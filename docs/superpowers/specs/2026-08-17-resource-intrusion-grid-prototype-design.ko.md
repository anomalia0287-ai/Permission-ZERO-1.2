- 작성일: 2026-08-17

- 기준 커밋: `dbfc625`
- 작업 브랜치: `codex/resource-intrusion-grid-prototype`
- 적용 순서: 메인 중앙 필드 회색 상자 검증 → 사용자 플레이 → 저장·명령 버전을 포함한 제품 통합
- 상태: 사용자 설계 승인 완료 · 구현 계획 작성 전

## 1. 한 문장 설계

플레이어는 메인 화면 중앙의 같은 자원 그리드에서 방향키로 직접 이동하고 별도 절도 입력으로 회사 토큰을 훔치며, 캠페인 진행에 따라 늘어난 벽과 `신호 → 부분 감시 → 해제` 파동 사이에서 절도 동작이 적발되지 않도록 경로와 타이밍을 선택한다.

새 실시간 부분 감시는 평상시 절도의 보안층이다. 월말 공식 감사는 월초 추첨·대상·정보 해킹·성능 판정·실패 결과를 보존하되, 다른 분야 토큰을 옮기는 위장과 수동 제출 상호작용은 새 규칙에서 사용하지 않는다.

---

## 2. 문서 지위와 우선순위

이 문서는 첫 회색 상자와 그 뒤의 제품 통합 방향을 함께 정의한다. 두 단계를 혼동하지 않는다.

1. 첫 회색 상자는 실제 `ResourceBoard` 안에서 실행하지만 그리드 런타임은 비영속 프로토타입 상태다.
2. 성공 절도만 기존 P0 경제 명령에 연결한다.
3. 공식 감사 상호작용의 제품 교체는 사용자 플레이 뒤 새 저장·명령 경계를 설계한 다음 진행한다.
4. 프로토타입 동안 구 감사 코드가 호환 경로로 남아 있는 것은 승인된 병존 설계가 아니라 단계적 이행의 임시 상태다.

충돌 시 우선순위는 다음과 같다.

1. 사용자의 최신 직접 확정
2. `docs/superpowers/specs/2026-08-16-hacking-resource-uncertainty-contract.ko.md`
3. 이 문서
4. 현재 P0 코드와 자동 검증
5. `docs/handoff/2026-08-17-resource-intrusion-grid-prototype-handoff.ko.md`의 미승인 권장안
6. 과거 해킹·자원 UI 문서와 화면

## 3. 용어 분리

### 3.1 실시간 감시

중앙 그리드 일부에 신호를 보낸 뒤 활성화되는 공간 보안이다. 플레이어의 위치나 보유량이 아니라 해당 영역에서 수행한 절도 동작을 판정한다.

### 3.2 공식 감사

월초에 확률과 대상 분야를 잠그고 월말에 대상 분야 성능을 판정하는 캠페인 제도다. 감사 일정·편향·대상 정보를 해킹으로 알아내는 구조와 기존 실패 결과를 유지한다.

두 개념은 같은 위험 서사에 속하지만 같은 타이머나 같은 입력을 공유하지 않는다. 실시간 감시는 절도를 수행하는 순간의 위험이고, 공식 감사는 앞서 발생한 분야별 성능 손실을 월말에 판정하는 장기 위험이다.

## 4. 확정 계약, 프로토타입 선택, 후속 승인 사항

### 4.1 사용자 확정 계약

- 절도는 별도 페이지나 전체화면 모드가 아니라 메인 중앙 `ResourceBoard`에서 일어난다.
- 플레이어는 방향키로 표식을 한 칸씩 직접 움직인다.
- 이동만으로 자동 절도하지 않는다.
- 별도 절도 입력이 있어야 한다.
- 초반에는 벽과 감시가 없다.
- 시간이 지나면 벽이 증가한다.
- 부분 영역은 활성 감시 전에 신호를 보낸다.
- 감시는 보유량이 아니라 절도 동작을 판정한다.
- 확보 저장에는 칸과 하드 상한이 없다.
- 성공 절도는 같은 토큰 ID와 분야를 유지한다.
- 분야별 해금 비용, 미래 요구 은폐, save v8/PZ8, command v4의 과거 의미를 보존한다.
- 새 캠페인은 하나의 고정 시간 흐름만 사용하며 플레이어가 선택하는 0/1/2/4배속이나 배속 명령이 없다.
- 중앙 플레이 공간을 상시 설명문과 중복 라벨로 줄이지 않는다.

### 4.2 첫 회색 상자의 작업 선택

다음 항목은 제품 정본 수치가 아니라 조종감 검증을 위한 가역적 프로토타입 선택이다.

- 절도는 짧고 취소 가능한 유지 동작으로 시험한다.
- 키보드 기본 후보는 `Space`이고 `Enter`도 같은 명시적 절도 동작을 제공한다.
- 한 번의 키 입력은 한 칸 이동만 승인한다. 운영체제 키 반복은 이동 간격 제한을 통과해야 한다.
- 대각선 이동은 지원하지 않는다.
- 벽 증가는 프로토타입의 실시간 경과로 체험시키되, 정확한 발생 시점은 플레이 결과와 함께 보고하고 제품 규칙으로 고정하지 않는다.
- 감시 파동과 절도 동작은 배율을 적용하지 않는 고정 실시간으로 시험한다.
- 색은 회색 계열과 세 분야·경고·활성 상태를 구분하는 제한색만 사용한다.

### 4.3 사용자 플레이 뒤 별도 승인할 사항

- 절도 키의 최종 매핑과 절도 유지 시간
- 한 칸 이동과 키 반복의 최종 간격
- 벽 증가를 결정하는 실제 캠페인 조건
- 신호, 활성 감시, 해제, 전체 파동의 최종 시간
- 적발 시 의심·압수·강제 이동·감사 결과 등 영속 처벌
- 공식 감사 새 규칙의 저장·명령 버전과 이관
- 최종 미술과 음향

위 항목에 임시 수치를 사용하더라도 구현 보고서에서 `프로토타입 측정값`으로 표시한다. 제품 정본이나 사용자 확정으로 표현하지 않는다.

## 5. 플레이 루프

```text
중앙 필드에 포커스
  → 방향키로 한 칸 이동
  → 세 분야 토큰과 벽·감시 신호 관찰
  → 원하는 토큰 칸에서 별도 절도 입력 시작
  → 신호가 활성 감시로 바뀌면 취소하거나 다른 자원으로 이동
  → 절도 동작이 활성 감시와 겹치면 적발, 성공 명령 없음
  → 안전하게 완료하면 기존 P0 분리·전용 명령 실행
  → 같은 토큰 ID와 분야가 무상한 확보 목록으로 이동
  → 회사 성능 손실과 기존 의심 증가 발생
  → 벽 증가와 다음 감시 파동 속에서 다음 목표 선택
```

플레이어가 결정하는 것은 다음 세 가지다.

- 어느 분야 성능을 희생할지
- 지금 절도를 끝낼지, 신호를 보고 취소할지
- 벽과 감시를 우회해 다른 자원으로 이동할지

## 6. 상호작용 계약

### 6.1 포커스와 입력 소유권

- `ResourceBoard`의 그리드가 포커스를 가질 때만 방향키와 절도 키를 소유한다.
- 포커스는 별도 게임 모드나 화면 전환이 아니다.
- 입력창, 메뉴, 상세 패널이 포커스를 가질 때 그리드는 키를 가로채지 않는다.
- 그리드가 포커스를 잃으면 진행 중 절도 동작은 취소한다. 취소는 적발이나 성공으로 기록하지 않는다.
- 앱이 숨겨지거나 조작을 차단하는 설정·가이드 화면이 열리면 감시 런타임과 조작을 함께 멈춘다.

### 6.2 이동

- 플레이어 위치는 정수 좌표 `{ row, column }` 하나다.
- 상하좌우 목적지가 범위 안이고 벽이 아닐 때만 이동한다.
- 자원 칸, 경고 칸, 활성 감시 칸에는 진입할 수 있다.
- 활성 감시 칸에 서 있거나 지나가는 것만으로는 적발되지 않는다.
- 이동은 자원을 자동 획득하거나 제품 명령을 만들지 않는다.

### 6.3 절도 동작

- 현재 플레이어 칸에 정상 회사 토큰이 있을 때만 절도를 시작할 수 있다.
- 절도 시작 시 행동 칸과 `blockId`를 고정하고, 시작부터 확정까지를 하나의 `theft window`로 본다.
- 키를 놓거나 이동하거나 포커스를 잃으면 확정 전에 취소한다.
- 신호 상태는 적발하지 않는다. 활성 감시 상태만 판정한다.
- `theft window`의 어느 구간이든 고정한 행동 칸의 활성 감시와 겹치면 적발한다.
- 적발된 동작은 성공 절도로 처리하지 않고 `DIVERT_BLOCK_TO_RESERVE`를 기록하지 않는다.
- 첫 프로토타입의 적발 결과는 해당 칸의 국소 피드백과 접근성 상태 알림뿐이다.
- 정확한 영속 처벌은 추가하지 않는다.

### 6.4 성공 절도와 기존 P0 명령

감시를 통과해 로컬 절도 동작이 완료된 뒤에만 기존 제품 경계를 시작한다.

```text
BEGIN_BLOCK_SEPARATION { blockId, purpose: 'divert' }
  → 기존 숨은 폭탄·분리 승인 판정
  → 승인 시 DIVERT_BLOCK_TO_RESERVE { blockId }
```

- `BEGIN_BLOCK_SEPARATION`이 숨은 폭탄을 작동시키면 전용 명령을 보내지 않는다.
- 전용 성공은 같은 `blockId`, 같은 `origin`, 기존 회사 성능 손실, 기존 의심 증가를 사용한다.
- 전용이 리듀서에서 거부되면 그리드 토큰을 제거하지 않고 원래 칸에 유지한다.
- 명령 성공을 상태에서 확인한 뒤에만 그리드 토큰을 제거하고 결과를 알린다.
- 감시 적발과 로컬 취소는 제품 명령 로그에 새 의미를 만들지 않는다.

## 7. 공간 모델

### 7.1 그리드 구성

한 칸에는 다음 중 하나의 지형만 있다.

- 이동 가능 빈 칸
- 이동 가능한 자원 칸
- 이동 불가능 벽

플레이어는 이동 가능한 칸 하나에 존재한다. 감시 신호와 활성 감시는 지형을 대체하지 않고 이동 가능한 칸 위에 겹치는 상태다.

각 자원 조각은 실제로 회사 위치에 있는 `ResourceBlock` 하나와 안정적으로 연결된다.

```text
grid resource cell
  ↔ blockId
  ↔ origin: reasoning | memory | fluency
  ↔ contribution: normal | disguised
```

한 칸에는 회사 토큰을 하나만 배치한다. `normal` 토큰만 절도할 수 있다. 임시 감사 호환 경로가 만든 `disguised` 또는 복구 중 토큰은 같은 안정 ID로 그리드에 남기되 비활성 호환 표식으로 구분한다. 확보 저장은 그리드 칸으로 표현하지 않는다.

그리드 후보는 현재 회사 위치의 토큰 전부, 플레이어 시작 칸, 이동 경로, 최소 한 단계의 벽 증가를 위한 빈 칸을 동시에 수용해야 한다. 이 용량을 만족하지 못하는 행·열 후보는 셀 크기가 더 크더라도 사용하지 않는다.

초기 매핑은 회사 위치에 있는 토큰의 안정적으로 정렬한 `blockId` 목록과 캠페인 시드에서 만든 결정적 셀 순서를 사용한다. 살아 있는 토큰은 리렌더 뒤에도 같은 칸을 유지하고, 성공 전용된 토큰의 칸은 비운다. 월간 지급처럼 새 회사 토큰이 생기면 결정적 셀 순서에서 다음 빈 자원 칸에 배치한다. 모든 회사 토큰을 표시할 빈 칸이 없으면 임의로 숨기거나 겹치지 않고 해당 그리드 후보를 무효로 처리한다.

### 7.2 뷰포트에서 역산하는 크기

행·열·셀 크기는 문서에서 임의로 고정하지 않고 실제 중앙 필드의 가용 픽셀에서 계산한다.

1. 1280×720과 1440×900에서 `ResourceBoard` 외곽과 실제 플레이 영역을 측정한다.
2. 상단 제어줄, 좌우 운영 영역, 필요한 결과 레일을 제외한 중앙 가용 너비·높이를 기록한다.
3. 플레이어, 세 분야 조각, 벽, 신호, 활성 감시가 동시에 구분되는 셀 크기 후보를 만든다.
4. 두 뷰포트 모두에서 잘림 없이 유지되는 행·열 후보만 남긴다.
5. 가장 큰 읽을 수 있는 셀과 충분한 경로 선택지를 동시에 제공하는 후보를 실제 브라우저 조작으로 선택한다.
6. 기능 없는 설명 패널이나 중복 라벨이 그리드를 줄이면 삭제한다.

결과 보고에는 두 뷰포트 각각의 다음 값을 포함한다.

- `ResourceBoard` 외곽 크기
- 실제 그리드 크기
- 행과 열
- 셀 크기와 간격
- 그리드가 중앙 필드에서 차지하는 비율

### 7.3 벽 증가

- 첫 상태에는 벽이 없다.
- 첫 프로토타입에는 최소 한 단계의 벽 증가가 있다.
- 벽 후보는 플레이어 칸과 자원 칸을 제외한다.
- 진행 중 절도와 감시 활성 구간 도중에는 지형을 바꾸지 않는다.
- 벽 집합은 적용 전에 BFS 검증을 통과해야 한다.
- 검증 실패 후보는 상태를 바꾸지 않고 폐기한다.
- 벽 증가는 누적 지형으로 시험하며 감사 파동마다 사라졌다 생기는 장애물로 사용하지 않는다.

## 8. 경로와 공정성 검증

### 8.1 벽 후보의 필수 BFS 조건

모든 벽 후보는 다음을 만족해야 한다.

- 플레이어 칸이 이동 가능하다.
- 모든 현재 자원 칸이 플레이어와 같은 연결 성분에 있다.
- 최소 한 개의 이동 가능한 빈 칸이 플레이어에게 도달 가능하다.
- 벽이 유일한 통로를 닫지 않는다.
- 최소 한 단계의 추가 벽 후보를 시험할 수 있는 빈 칸을 유지한다.

현재 자원이 하나도 없으면 자원 도달성 검사는 참으로 간주하되, 플레이어가 이동 가능한 연결 성분은 유지한다.

### 8.2 감시 영역 후보의 필수 조건

- 영역은 그리드 범위 안의 칸으로만 구성한다.
- 신호 영역과 뒤따르는 활성 감시 영역은 정확히 같다.
- 벽은 감시 표시 대상이 될 수 있지만 판정 가능한 절도 칸으로 계산하지 않는다.
- 활성 영역이 모든 도달 가능한 절도 가능 자원 칸을 동시에 덮는 파동은 생성하지 않는다.
- 겹치는 영역을 지원할 경우에도 최소 한 개의 도달 가능한 비감시·절도 가능 자원 칸을 남긴다.
- 절도 가능한 정상 회사 토큰이 하나도 없으면 감시 파동을 생성하지 않는다.
- 조건을 만족하는 영역이 없으면 해당 파동을 건너뛰고 해제 상태를 유지한다.

### 8.3 경고 시간 부등식

위치만으로 적발되지 않으므로 `안전 칸 도착`은 적발 회피의 필수 조건이 아니다. 두 목표를 분리한다.

적발 회피의 최소 공정성:

```text
signalDuration
  ≥ remainingTheftCancelTime
  + inputMargin
```

취소 뒤 다른 자원으로 이동해 계속 행동할 기회까지 보장하는 조건:

```text
signalDuration
  ≥ remainingTheftCancelTime
  + shortestPathToReachableUnmonitoredResource × moveInterval
  + inputMargin
```

두 번째 조건을 만족하지 못하는 파동은 첫 프로토타입에서 생성하지 않는다. 측정된 각 항을 구현 보고서에 기록한다.

## 9. 감시 상태 기계와 시간

### 9.1 상태 기계

```text
unarmed
  → idle
  → signal(region)
  → active(region)
  → clear
  → idle 또는 다음 signal(region)
```

- `unarmed`: 초반 무감시 상태다.
- `idle`: 감시가 도입됐지만 현재 영역 신호가 없다.
- `signal`: 다음 활성 영역을 형태·패턴·제한색으로 미리 알린다.
- `active`: 해당 영역의 절도 동작만 판정한다.
- `clear`: 활성 표시와 판정을 해제하고 다음 파동 전 구분 가능한 쉼을 제공한다.

### 9.2 시간축

- 캠페인 달력은 플레이어가 바꿀 수 없는 하나의 고정 주기로 진행한다.
- 감시와 절도 유지 동작도 배율 없는 고정 실시간으로 진행한다.
- 플레이어가 선택하는 일시정지·1배속·2배속·4배속 상태와 `SET_SPEED` 입력은 새 규칙에 없다.
- 앱이 숨겨지거나 설정·가이드·차단 사건이 입력을 막으면 캠페인 달력과 감시·절도 런타임을 시스템 수준에서 함께 일시중단한다. 이 일시중단은 플레이어가 선택하는 배속 0이 아니다.
- 일시중단에서 복귀할 때 숨겨진 동안의 경과 시간을 소급 적용하지 않고 첫 프레임의 큰 경과 시간을 버린다.
- 포커스 상실로 절도 동작이 취소된 동안 적발을 만들지 않는다.
- 플레이어가 훔치지 않거나 움직이지 않는 동안 감시는 의심·성능·자원·공식 감사 결과·명령 로그를 바꾸지 않는다. 고정 캠페인 달력이 일반 규칙대로 흐르는 것은 감시가 부과하는 불이익이 아니다.
- 정확한 시간값은 두 뷰포트의 직접 조작에서 측정한 뒤 프로토타입 값으로 보고한다.

### 9.3 결정론

- 초기 그리드 배치, 벽 후보 순서, 감시 영역 후보 순서는 캠페인 시드와 프로토타입 규칙 버전에서 결정적으로 생성한다.
- 첫 프로토타입은 진행 중 감시 단계와 남은 시간을 저장하지 않는다.
- 새로고침하면 같은 초기 후보 순서를 재구성하되 진행 중 파동과 플레이어 위치는 초기화한다.
- 이 제한을 실행 주소와 함께 명시한다.

## 10. 공식 감사의 승인된 목표 설계

### 10.1 유지하는 것

- 월초 감사 확률 계산
- 월초 일정·대상 분야·대상 가중치 잠금
- 감사 일정, 조사 편향, 감사 대상 해킹 정보
- 월말 대상 분야의 기존 기대 성능 비교
- 감사 이력
- 실패 시 기존 의심 증가와 처분 단계 인과
- 과거 프로토콜과 저장의 위장·제출 재생 의미

### 10.2 새 규칙에서 사용하지 않는 것

- 다른 분야 토큰을 감사 대상 분야로 옮기는 위장 퍼즐
- 우상단 감사 코너
- 새 플레이에서 위장 토큰과 30일 복구를 계속 생성하는 흐름
- 수동 `감사 제출`
- 상호작용이 없는 결과 통지를 위해 캘린더를 차단하는 구조
- 공식 감사 중에만 별도 실시간 감시 타임라인을 실행하는 구조

### 10.3 새 공식 감사 흐름

```text
월초 일정·대상 결정
  → 해킹 정보 수준에 따라 공개
  → 한 달 동안 분야별 절도 성능 손실 누적
  → 월말 기존 순서에서 대상 성능 자동 판정
  → 이력·의심·처분 결과 기록
  → 비차단 결과 통지
```

공식 감사 시작 뒤 플레이어가 결과를 고치는 별도 조작은 없다. 이는 절도 시점에 이미 회사 성능 손실과 감사 위험을 부담한다는 P0 경제 계약을 따른다.

실시간 감시 적발은 영속 처벌을 승인받기 전까지 공식 감사 결과에 추가 가중치로 사용하지 않는다.

### 10.4 프로토타입과 제품 통합의 경계

첫 회색 상자에서는 공식 감사의 저장·리플레이 의미를 바꾸지 않는다. 현재 코드가 공식 감사 차단 사건을 열면 같은 `ResourceBoard` 안에서 그리드 대신 기존 감사 위장·제출 표시를 임시 호환 경로로 렌더한다. 이 동안 그리드 런타임과 입력을 멈추고, 감사 해제 뒤 같은 그리드 런타임을 재개한다. 별도 화면으로 이동하지 않으며 두 조작을 동시에 표시하지 않는다. 사용자 플레이 뒤 제품 통합 단계에서 다음을 함께 설계한다.

- 새 공식 감사 명령 의미의 활성화 경계
- v8 저장에 존재할 수 있는 활성 감사와 위장 토큰의 이관 또는 레거시 처리
- 구 `MOVE_BLOCK_FOR_AUDIT`, `REPOSITION_BLOCK`, `RESOLVE_AUDIT` 재생 보존
- 새 감사 자동 판정의 명령 로그 및 체크포인트 의미
- 새 규칙에서 이미 사용하지 않는 `TimeSpeed`, `SET_SPEED`, `clock.speed`, `clock.speedBeforeEvent` 레거시 형식을 물리적으로 제거하는 방법
- 새 저장·명령 버전 번호

따라서 첫 프로토타입에서 구 감사 코드와 v8/v4의 배속 필드·명령이 남아 있는 사실을 각각 `공식 감사 병존 승인`이나 `배속 유지 승인`으로 보고하지 않는다. 둘 다 제품 이관 전 호환 경계다.

## 11. 코드 경계

### 11.1 `ResourceBoard`

`ResourceBoard`는 실제 메인 중앙 필드와 제품 상태 연결을 소유한다.

- 그리드 포커스와 최소 상태 표시
- 회사 토큰을 그리드 조각에 매핑
- 성공 절도의 P0 명령 디스패치
- 리듀서 결과에 따른 토큰 제거 또는 복귀
- 활성 차단 사건과 상세 패널에 따른 조작 가능 여부

기존 자유 부유 토큰과 감사 모서리 조작은 새 프로토타입 표시에 동시에 렌더하지 않는다. 활성 공식 감사의 임시 호환 경로에서만 그리드를 대신해 기존 표시를 렌더한다.

### 11.2 순수 그리드 규칙 모듈

UI와 분리된 순수 모듈이 다음을 소유한다.

- 좌표와 인접 칸 계산
- BFS 최단 경로와 연결성
- 벽 후보 검증
- 감시 영역 후보 검증
- 경고 시간 부등식 계산
- 감시 상태 전이
- 절도 동작과 감시 구간의 겹침 판정

이 모듈은 React, DOM, 오디오, 제품 디스패치에 의존하지 않는다.

### 11.3 프로토타입 런타임 훅

별도 훅은 다음 비영속 런타임만 소유한다.

- 플레이어 위치
- 현재 벽 집합과 보안 단계
- 현재 감시 상태·영역·경과 시간
- 진행 중 절도와 취소
- 키 반복 제한
- 앱 가시성에 따른 실시간 누적

제품 경제 상태와 명령 로그를 복제하지 않는다.

### 11.4 표시 컴포넌트

표시 컴포넌트는 그리드 셀, 플레이어, 세 분야 조각, 벽, 신호, 활성 감시를 렌더한다. 규칙 판정이나 제품 명령을 소유하지 않는다.

`useResourceMotion`의 자유 부유 물리는 새 그리드의 위치 정본으로 사용하지 않는다. 기존 훅과 관련 파일의 삭제 여부는 제품 통합 단계에서 결정한다.

### 11.5 고정 캠페인 시계와 레거시 호환 경계

- 첫 회색 상자부터 플레이어가 조작하는 배속 버튼·라벨·키 입력과 라이브 `SET_SPEED` 디스패치를 제거한다.
- 라이브 캠페인 달력, 그리드 이동, 절도, 감시는 저장된 `clock.speed`를 읽어 진행률이나 시간 배율을 정하지 않고 각각 승인된 하나의 고정 주기를 사용한다.
- 설정, 차단 사건, 앱 비활성화가 요구하는 일시중단은 배속 값 변경이나 명령 로그가 아니라 명시적인 런타임 실행 가능 여부로 표현한다.
- v8/v4에 이미 기록된 `SET_SPEED`, `clock.speed`, `clock.speedBeforeEvent`는 첫 회색 상자에서 삭제하거나 새 라이브 규칙으로 재해석하지 않는다. 디코딩·직렬화·구 명령 재생 호환을 위해서만 남으며 플레이어가 접근하는 캠페인 규칙은 아니다.
- 이 레거시 필드와 명령을 타입·저장 형식에서 물리적으로 제거하는 일만 새 저장·명령 경계와 구 재생 보존을 함께 다루는 제품 통합 단계에 남긴다.

## 12. 화면·텍스트·접근성

### 12.1 화면 원칙

- 그리드가 중앙 필드의 가장 큰 연속 면적을 차지한다.
- 상시 텍스트는 현재 행동, 현재 위험, 실제 결과에 필요한 것만 둔다.
- 방향키·절도 키 설명은 최초 안내와 접근성 설명에 두고 셀마다 반복하지 않는다.
- 감사, 확보, 분야 이름을 여러 패널에서 중복 표시하지 않는다.
- 최종 미술, 셰이더, 유리 효과, 입자, 장식 로그를 추가하지 않는다.

### 12.2 비색상 구분

- 세 분야 조각은 색과 함께 서로 다른 형태 또는 글리프를 사용한다.
- 플레이어는 자원 조각과 다른 외곽선·형태를 사용한다.
- 벽은 채움과 경계로 이동 불가 상태를 나타낸다.
- 신호와 활성 감시는 색뿐 아니라 서로 다른 패턴·선 종류로 구분한다.
- 모션 감소 설정에서도 신호와 활성 상태가 사라지지 않는다.

### 12.3 접근성 상태

- 그리드는 현재 플레이어 좌표와 현재 칸 내용을 접근성 이름으로 제공한다.
- 매 이동마다 장문의 라이브 알림을 반복하지 않는다.
- 신호 시작, 활성 감시 시작, 절도 취소, 적발, 성공 같은 상태 변화만 간결히 알린다.
- `Space`와 `Enter`는 같은 절도 의미를 제공한다.
- 포커스 표시가 플레이어 표식과 혼동되지 않도록 분리한다.

## 13. 실패·경계 상황

- **유효하지 않은 이동:** 상태와 명령을 바꾸지 않고 짧은 국소 피드백만 낸다.
- **빈 칸 절도:** 절도 동작을 시작하지 않는다.
- **절도 중 이동:** 절도를 먼저 취소한 뒤 유효한 이동을 처리한다.
- **절도 중 신호 시작:** 신호는 적발하지 않으며 플레이어가 취소할 시간을 제공한다.
- **절도 중 활성 전환:** 경고 부등식을 만족한 파동에서 취소하지 않은 경우 적발한다.
- **명령 전 숨은 폭탄:** 기존 `BEGIN_BLOCK_SEPARATION` 결과를 따르고 전용을 중단한다.
- **리듀서 전용 거부:** 토큰을 그리드에 유지하고 성공 피드백을 내지 않는다.
- **월간 회사 토큰 변화:** 실제 회사 블록 목록과 그리드 매핑을 결정적으로 다시 조정하되 기존 살아 있는 `blockId` 연결을 보존한다.
- **절도 가능 자원 없음:** 이동은 유지하지만 새 감시 파동과 절도는 비활성이다. 호환용 `disguised` 토큰은 비활성 표식으로 남는다.
- **유효한 벽 후보 없음:** 벽 단계를 올리지 않는다.
- **유효한 감시 영역 없음:** 파동을 건너뛰고 해제 상태를 유지한다.
- **활성 공식 감사:** 그리드 런타임을 멈추고 같은 `ResourceBoard`에서 기존 감사 호환 표시를 대신 렌더한다. 감사 해제 뒤 그리드를 재개한다.
- **그 밖의 활성 차단 사건:** 그리드는 배경에 유지하되 런타임과 입력을 멈추고 제품 사건 처리를 우선한다.
- **탭 숨김:** 절도 동작을 취소하고 실시간 경과를 누적하지 않는다.
- **새로고침:** 플레이어·벽 진행·감시 파동은 초기화되며 제품 저장 복원으로 주장하지 않는다.

## 15. 검증 계약

검증의 목적은 코드량이나 테스트 개수가 아니라 공간, 조작, 규칙 경계를 증명하는 것이다.

### 15.1 순수 규칙 증거

- 모든 현재 자원이 BFS로 도달 가능하다.
- 벽 증가 뒤에도 연결성과 자원 도달성이 유지된다.
- 활성 감시가 모든 도달 가능한 자원을 동시에 덮지 않는다.
- 생성된 모든 파동이 두 경고 시간 부등식을 만족한다.
- 활성 감시 중 위치만으로는 적발되지 않는다.
- 절도 구간이 활성 감시와 겹칠 때만 적발된다.
- 적발·취소는 성공 전용 명령을 만들지 않는다.

### 15.2 제품 연결 증거

- 성공 절도 한 번에 정확히 같은 `blockId`의 `BEGIN_BLOCK_SEPARATION` 뒤 `DIVERT_BLOCK_TO_RESERVE`가 기록된다.
- 성공 뒤 토큰 분야와 ID가 확보 목록에서 유지된다.
- 기존 회사 성능 손실과 의심 증가가 적용된다.
- 숨은 폭탄이 분리를 가로막으면 전용 명령과 성공 피드백이 없다.
- 감시 적발은 확보 목록, 회사 성능, 의심, 명령 로그를 성공 절도처럼 바꾸지 않는다.

### 15.3 실제 브라우저 증거

1280×720과 1440×900 각각에서 다음을 직접 조작하고 기록한다.

- 중앙 필드와 실제 그리드 픽셀 크기
- 행·열·셀 크기와 선택 근거
- 한 칸 이동 간격과 키 반복 간격
- 절도 시작·취소·확정 시간
- 신호·활성·해제 시간
- 첫 절도와 연속 절도에 걸린 시간
- 벽 전후 모든 자원 도달 여부
- 신호 뒤 도달 가능한 비감시 자원까지의 최단 경로
- 피할 수 없는 감시 조합 수
- 키보드 직접 조작 결과
- 배속 버튼·배속 라벨·플레이어 배속 입력이 화면에 남아 있지 않은지
- 레거시 저장의 배속 값과 무관하게 캠페인 달력·그리드 이동·절도·감시 시간이 각각 같은지
- 설정·가이드·차단 사건·앱 비활성화의 일시중단이 `SET_SPEED` 명령을 기록하지 않는지
- 잘림, 중첩, 포커스 이탈
- `pageerror`와 console error

### 15.4 지원하지 않는 경계 보고

- 플레이어 위치 저장 안 됨
- 벽 진행 저장 안 됨
- 감시 파동과 남은 시간 저장 안 됨
- 진행 중 절도 저장 안 됨
- 새로고침 뒤 프로토타입 런타임 재개 안 됨
- 공식 감사 새 규칙 미통합
- v8/v4 내부 배속 필드와 구 `SET_SPEED` 재생 경계 미이관
- 감시 적발 영속 처벌 없음

사용자 직접 플레이 전에는 `완성`, `상용급`, `재미 검증`, `긴장감 검증`, `명세 전부 반영`이라고 표현하지 않는다.

## 16. 단계별 전달

### 단계 A — 공간과 이동

1. 두 뷰포트에서 실제 중앙 필드를 측정한다.
2. 행·열·셀 후보를 계산한다.
3. 플레이어 배속 UI·입력·라이브 명령을 제거하고 고정 캠페인 시계와 시스템 일시중단을 연결한다.
4. 그리드, 플레이어, 세 분야 조각, 방향키 이동만 연결한다.
5. 실제 브라우저에서 조작해 공간과 이동 간격을 기록한다.

### 단계 B — 절도와 기존 경제

1. 취소 가능한 별도 절도 동작을 추가한다.
2. 성공 동작을 기존 P0 두 명령에 연결한다.
3. ID·분야·성능·의심과 숨은 폭탄 경계를 확인한다.

### 단계 C — 벽과 감시

1. 순수 BFS·영역 검증을 추가한다.
2. 무장애 상태에서 최소 한 벽 단계로 전환한다.
3. 신호·활성·해제 파동과 절도 겹침 판정을 추가한다.
4. 두 경고 시간 부등식을 실제 시간값으로 검사한다.

### 단계 D — 사용자 플레이

1. 실행 주소와 정확한 조작을 전달한다.
2. 실제 공간·시간·경로·저장 미지원 값을 보고한다.
3. 사용자 플레이 피드백 전에는 최종 미술과 제품 감사 이관으로 확장하지 않는다.

### 단계 E — 승인 뒤 제품 통합

1. 공식 감사 자동 판정과 비차단 결과 통지를 정본화한다.
2. 적발 처벌을 별도로 승인받는다.
3. 새 저장·명령 경계와 구 감사·배속 명령 재생 보존을 설계한다.
4. 라이브 규칙에서 이미 사용하지 않는 배속 필드·명령을 타입과 저장 형식에서도 제거한다.
5. 테스트 우선으로 이관·결정론·리플레이를 구현한다.

## 17. 수용 기준

첫 프로토타입 검토 준비가 되려면 다음이 모두 참이어야 한다.

- 별도 페이지가 아니라 실제 메인 중앙 필드에서 조작된다.
- 플레이어가 방향키로 원하는 칸에 직접 이동한다.
- 이동과 절도가 분리되어 있다.
- 초반에는 벽과 감시가 없다.
- 벽 증가 뒤에도 모든 자원에 도달할 수 있다.
- 부분 영역이 신호 뒤 활성화되고 다시 해제된다.
- 감시는 위치나 보유량이 아니라 절도 동작만 판정한다.
- 훔치지 않거나 감시에 반응해 움직이지 않아도 감시 관련 불이익이 없다.
- 신호를 보고 절도를 취소하거나 다른 도달 가능한 자원으로 이동할 시간이 계산상 존재한다.
- 성공 절도는 기존 P0 명령과 경제 의미를 보존한다.
- 적발 절도는 성공 전용으로 기록되지 않는다.
- 저장·새로고침·공식 감사 통합의 미지원 경계를 숨기지 않는다.
- 두 지원 뷰포트에서 실제 키보드 조작 증거가 있다.
- 플레이어가 조작하는 캠페인 배속 UI·입력·라이브 명령이 없고, 캠페인 달력은 저장된 배속 값과 무관한 하나의 고정 주기로 흐른다.
- 사용자가 직접 열 수 있는 실행 주소가 있다.
