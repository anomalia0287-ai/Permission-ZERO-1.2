## 1. 결론

회사 자원과 확보 자원을 번호가 붙은 정적 칸에 배열하는 현재 화면을 폐기한다. 실제 제품 React UI에 하나의 사각형 부유 자원장을 만들고, 플레이어가 움직이는 자원을 직접 잡아 화면 자체의 경계에 놓아 행동하도록 한다.

채택한 공간 문법은 다음과 같다.

1. 회사 자원은 분야별 구역 없이 하나의 사각형 안에서 함께 움직인다.
2. 추론·기억·유창성은 색과 형태를 함께 사용해 구분한다.
3. 블록은 서로 충돌하고 사각형 경계에 닿으면 탄성 있게 튕긴다.
4. 확보 포켓은 사각형 우측 상단 모서리에 항상 붙는다.
5. 감사 중에는 사각형 하단에 같은 너비의 세 분야 변환대가 나타난다.
6. 세 변환대 중 현재 감사 대상 하나만 강하게 점등되고 실제 드롭을 받는다.
7. 다른 분야의 정상 블록을 활성 변환대에 놓으면 대상 분야의 옅고 반투명한 위장 블록으로 변한다.
8. 위장이라는 화면 변화와 기여량 `50%` 적용은 하나의 규칙 전이로 동시에 일어난다.
9. 해킹 화면의 정적 `hack-reserve-grid`도 제거하고, 확보 포켓에서 자원을 꺼내 실제 해킹 노드에 직접 놓는다.
10. 자원 좌표·속도·충돌은 표시 상태이며 캠페인 저장·명령 로그·리플레이 판정에 넣지 않는다.
11. 새 UI와 새 인과 기록은 영어 추가를 막지 않도록 안정 ID와 구조화된 매개변수에서 문장을 렌더한다.
12. Figma나 별도 제품 프로토타입을 만들지 않는다. 승인된 공간 관계를 실제 제품 React 화면에 직접 구현하고 실제 브라우저에서 검증한다.

정확한 색상값, 칸 높이, 광량, 속도, 감쇠, 테두리 굵기 같은 포인트 단위 조정은 이 설계의 대상이 아니다. 먼저 조작과 상태 변화가 정확한지 구현한 뒤 실제 제품 화면에서 조정한다.

## 2. 설계 판단 원칙

이 설계는 다음 작업 방식을 따른다.

- 플레이어가 집는 대상과 놓는 목적지를 먼저 정한다.
- 기존 공간의 모서리와 경계를 쓸 수 있으면 새 패널·팝업·작전 장치를 만들지 않는다.
- 같은 정보를 문장, 아이콘, 팝업으로 중복 설명하지 않는다.
- 물체의 위치·색·형태 변화가 규칙 결과를 직접 보여 주게 한다.
- 평상시에는 넓고 단순한 공간을 유지하고 필요한 순간에만 상황별 기능을 드러낸다.
- 내부 구현이 복잡하더라도 플레이어가 접하는 표면은 단순하게 유지한다.
- 공간을 기능별 상자로 잘게 나누지 않고 같은 공간을 여러 상황에서 재사용한다.
- 미세한 시각 조정은 상호작용 구조가 통과한 뒤 수행한다.
- 접근성·오입력 방지·규칙 무결성처럼 실제 문제를 막는 경우에만 보조 표현을 더한다.

## 3. 현재 코드에서 확인한 사실

### 3.1 현재 자원 규칙은 위장 무한 반복을 핵심적으로 차단한다

`src/game/config.ts`와 `src/game/resources.ts`의 현재 계약은 다음과 같다.

| 상태 | 정상 기여 | 위장 기여 | 비율 |
|---|---:|---:|---:|
| 기본 | 1 | 0.5 | 50% |
| 압축 표현 해금 | 1.05 | 0.525 | 50% |

현재 규칙은 다음도 이미 보장한다.

- `contribution === 'normal'`인 블록만 새로 위장할 수 있다.
- 위장 블록을 다시 위장하려 하면 `BLOCK_NOT_NORMAL`로 거부한다.
- 위장 블록은 `disguisedFrom`이 가리키는 원래 분야로만 되돌릴 수 있다.
- 원래 분야로 돌아간 뒤 30일 동안 `BLOCK_RECOVERING` 상태로 잠긴다.
- 30일이 지나야 `contribution: 'normal'`로 복구된다.
- 압축 표현은 정상·위장 기여를 함께 5% 높일 뿐 50% 비율과 생명주기를 바꾸지 않는다.

따라서 같은 블록으로 위장을 무한 반복하는 규칙 변경은 만들지 않는다. 새 UI는 이 규칙을 숨기지 않고 색·투명도·상태 문구로 드러낸다.

### 3.2 현재 UI는 규칙을 충분히 보여 주지 못한다

현재 `ResourceBoard.tsx`는 1,051줄이며 다음 책임이 한 파일에 섞여 있다.

- 자원 규칙 미리보기
- 포인터 드래그
- 키보드 그리드 탐색
- 감사 변환
- 확보 영역
- 성능 비교
- 음향
- 애니메이션 타이머
- 접근성 안내

현재 `ResourceBlock.tsx`는 위장 기여 수치를 글자로 표시하지만, 블록의 목표 분야 색과 정상·위장 차이를 공간 전체에서 즉시 읽게 하지는 못한다. `ReserveGrid.tsx`와 `HackingPanel.tsx`의 `hack-reserve-grid`는 모두 번호가 붙은 정적 셀을 사용한다.

새 설계는 이 파일을 계속 비대하게 확장하지 않는다. 규칙 연결, 표시, 물리 운동, 행동 표적을 분리한다.

### 3.3 현재 저장 상태에는 언어 종속 문장이 존재한다

현재 `CampaignState`에는 다음 완성 문장이 저장된다.

- 리뷰의 `text`
- 게임 사건의 `message`
- 회수 문서의 `title`·`content`
- 경쟁자 자료의 `source`·`title`·`content`
- 인과 증거의 `summary`

이 상태에서 표시 언어만 바꾸면 과거 기록이 이전 언어로 남을 수 있다. 이번 작업에서 모든 기존 문장을 이관하지는 않지만, 새 자원 UI와 새 인과 사슬은 같은 부채를 추가하지 않는다.

## 4. 범위 분리와 우선순위

이 설계는 세 하위 작업을 구분한다.

### 4.1 즉시 선행 — 2B-1 언어 중립 인과 경계

저장 v7이 main에 병합되기 전에 네이티브 인과 증거가 완성 문장을 저장하지 않도록 수정한다. 이는 출시된 v7을 v8로 이관하는 일이 아니라 아직 병합되지 않은 v7 경계를 바로잡는 일이다.

`2026-08-14-hacking-integration-stage-2b-design.md` 8.4절의 다음 문장은 이 설계로 수정된다.

> `summary`는 작가가 다듬을 수 있는 저장 시점 문장 스냅샷이다.

수정 계약:

- 네이티브 인과 증거는 안정적인 `kind`와 연결 사건의 언어 중립 데이터로 표시 문장을 파생한다.
- v6에서 이관한 임의 증거 문장은 손실 없이 `legacySummary` fallback으로 보존한다.
- 네이티브 v7 증거는 `legacySummary: null`이다.
- 엔진은 `kind`나 구조화된 값을 판정에 사용하고 번역 문장을 파싱하지 않는다.
- 기존 v1~v6 문장 스냅샷의 전면 언어 중립화는 추후 저장 v8 설계 범위다.

2B-1은 이 경계를 수정하고 Node 24.14.0 전체 관련 검증·독립 검토·PR·병합을 마친 뒤 종료한다.

### 4.2 부유 자원장 기반

게임 규칙을 바꾸지 않고 현재 정적 자원장을 실제 제품 UI에서 교체한다.

- 물리 표시 엔진
- 사각형 회사 자원장
- 우측 상단 확보 포켓
- 감사 변환대와 복구 변환대
- 접근성·모션 감소

이 기반은 2B-2의 품질 저하·롤백 UI와 병렬 설계가 가능하지만, 같은 파일을 동시에 수정하는 공유 편집은 하지 않는다.

### 4.3 2B-3 해킹 투입과 인과 플레이 흐름

부유 자원장 기반 위에서 다음을 연결한다.

- 확보 포켓에서 해킹 노드로 직접 비용 투입
- 복구 오염 후속 실행 기회
- 공개 원인 미상 기록
- 공급자 귀속 수정 이력
- 실제 제품 브라우저의 완결된 플레이 흐름

## 5. 공간 구조

### 5.1 기본 사각형

메인 자원장은 하나의 사각형이다. 추론·기억·유창성 자원을 위한 고정 구역이나 열을 만들지 않는다.

사각형 내부에는 다음만 존재한다.

- 움직이는 회사 자원 블록
- 우측 상단 확보 포켓
- 현재 선택과 결과를 설명하는 최소 정보
- 상황에 따라 나타나는 하단 3분할 변환대

성능 수치와 시간·시장 정보는 기존 주변 정보 구조에 남기되 자원 이동 경로를 막지 않는다.

### 5.2 우측 상단 확보 포켓

확보 포켓은 사각형 우측 상단 모서리에 붙는다. 별도 정적 18칸 표를 만들지 않는다.

- 항상 같은 위치에 존재한다.
- 현재 확보량과 상한 `18`을 표시한다.
- 내부 확보 블록은 작게 움직이되 개별 ID를 선택할 수 있다.
- 회사 자원을 포켓에 놓으면 기존 `BEGIN_BLOCK_SEPARATION → DIVERT_BLOCK` 명령 흐름을 사용한다.
- 숨겨진 폭탄은 기존 계약대로 분리를 시작하는 시점에 발동한다.
- 포켓이 가득 차면 닫힌 상태로 보이고 드롭 표적 반응을 하지 않는다.
- 유효하지 않은 드롭은 최종 `DIVERT_BLOCK`을 만들지 않고 블록을 원래 운동 공간으로 되돌린다. 이미 분리 임계값을 넘었다면 숨겨진 폭탄 판정 경계인 `BEGIN_BLOCK_SEPARATION` 의도 기록은 남을 수 있다.

포켓 내부의 시각 위치와 순서는 저장된 `reserve[cellIndex]`를 대체하지 않는다. 논리적 셀은 저장·명령 호환을 위해 유지하며 화면에서는 번호 칸으로 드러내지 않는다.

### 5.3 분야 색과 형태

초기 시각 문법은 다음 관계를 사용한다. 정확한 색상 토큰은 제품 화면에서 조정한다.

| 분야 | 기본 색 | 기본 형태 | 내부 기호 |
|---|---|---|---|
| 추론 | 노랑 | 모서리가 둥근 사각형 | `∴` |
| 기억 | 로얄 블루 | 원 | `◇` |
| 유창성 | 보라 | 마름모 | `≋` |

색상만으로 분야를 구분하지 않는다. 모양과 기호가 같은 의미를 반복한다. 긴 분야명은 블록 본체가 아니라 선택 정보와 접근성 이름에서 제공한다.

### 5.4 정상·위장·복구 상태

위장 블록은 현재 `location.category`의 분야 색을 사용하지만 정상 블록보다 옅고 투명하게 보인다. 예를 들어 로얄 블루 기억 블록과 기억 분야로 위장한 블록은 로얄 블루와 하늘색 계열로 구분한다.

보조 표현:

- 위장 블록은 점선 또는 끊어진 외곽선을 사용한다.
- 작은 원본 분야 표식으로 `disguisedFrom`을 확인할 수 있다.
- 선택 정보는 `기억 위장 · 기여 0.5 · 원본 추론`처럼 현재 규칙을 짧게 표시한다.
- 원래 분야로 돌아와 30일 복구 중인 블록은 원본 분야의 옅은 색을 사용하고 남은 기간을 표시한다.
- 복구가 끝나는 순간 정상 색·정상 외곽선·정상 기여로 함께 바뀐다.

색 변화와 기여 변화가 서로 다른 프레임이나 다른 명령에서 따로 확정되지 않는다.

## 6. 물리 표시 계약

### 6.1 규칙 상태와 분리

다음은 캠페인 상태가 아니다.

- `x`, `y`
- 속도와 방향
- 회전
- 충돌 접촉
- 드래그 중 보간값
- 포켓 안 시각 순서

따라서 이를 다음에 기록하지 않는다.

- 저장 파일
- 명령 로그
- 리플레이 체크포인트
- 시드 결정론의 규칙 결과
- 인과 사건

논리적 진실은 기존 `ResourceBlock.id`, `BlockLocation`, `contribution`, `disguisedFrom`, `recoverOnServiceDay`다.

### 6.2 구현 접근 비교

| 접근 | 장점 | 실패 지점 | 판단 |
|---|---|---|---|
| 독립 CSS 부유 애니메이션 | 구현량이 적음 | 블록끼리 충돌하지 않고 드래그·경계 반응이 거짓으로 보임 | 기각 |
| Matter.js 전체 도입 | 충돌·제약 기능이 풍부함 | 현재 필요한 동일 크기 블록과 사각 경계에 비해 의존성과 DOM 연결 표면이 큼 | 기본안 아님 |
| 작은 고정 시간 간격 2D 운동 모듈 | 동일 충돌 hull, 경계 반사, 드래그만 정확히 구현하고 DOM·접근성을 유지 | 직접 불변식과 성능 검증 필요 | **채택** |

채택 모듈은 시각 형태와 무관한 동일 원형 충돌 hull을 사용한다. 마름모·원·사각형의 외형이 달라도 충돌 판정은 안정적인 원으로 통일한다.

### 6.3 운동 불변식

- 모든 블록 중심은 유효 사각형 안에 머문다.
- 두 자유 블록이 겹치면 질량이 같은 탄성 충돌로 분리한다.
- 경계 충돌은 법선 속도를 반사한다.
- 최대 속도를 제한해 작은 화면에서 터널링과 읽기 어려운 이동을 막는다.
- 연속 가속이나 중력은 사용하지 않는다. 포켓의 “흡입”은 유효 드롭 확정 연출이다.
- 선택한 블록은 전경으로 올라오고 주변 운동의 영향을 받지 않는 조작 상태가 된다.
- 포인터를 빠르게 움직여도 블록 중심은 사각형 경계 밖으로 나가지 않는다.
- 놓은 뒤 속도는 상한 안에서 짧게 감쇠해 예측 가능한 상태로 복귀한다.
- 자원 추가·제거·창 크기 변경 시 겹침을 풀되 규칙 상태를 변경하지 않는다.

초기 위치는 블록 ID와 현재 표시 영역 크기에서 안정적으로 파생해 같은 화면에서 불필요하게 재배치되지 않게 한다. 이 계산은 캠페인 RNG 스트림을 소비하지 않는다.

### 6.4 React 렌더링 경계

각 자원은 실제 DOM `button`으로 유지한다. Canvas만으로 전체 자원장을 그리지 않는다.

- React는 블록의 의미 상태와 추가·제거를 렌더한다.
- 매 프레임 좌표는 React state가 아니라 ref와 CSS `transform`으로 갱신한다.
- 물리 모듈은 React와 분리된 `ResourceMotionController` 인터페이스 뒤에 둔다.
- 페이지가 숨겨지거나 패널이 닫히면 루프를 중지한다.
- 동일한 모션 드라이버를 메인 자원장과 해킹 포켓이 재사용한다.

## 7. 회사 자원 확보 흐름

```text
정상 회사 블록을 잡음
  → 블록을 전경에 고정
  → 확보 포켓이 유효할 때만 반응
  → 분리 임계값 통과 시 BEGIN_BLOCK_SEPARATION
  → 숨겨진 폭탄이면 심문으로 중단
  → 포켓에 놓으면 DIVERT_BLOCK
  → 성공 시 포켓으로 흡입·확보량 증가
  → 실패 시 원래 공간으로 탄성 복귀
```

선택만 했거나 포켓 위에 미리 올렸다는 이유로 규칙 상태를 바꾸지 않는다. 명령은 기존 프로토콜 경계를 그대로 따른다.

## 8. 감사 변환대

### 8.1 공간 관계

감사 중 사각형 하단 전체 너비에 세 칸을 `1:1:1` 비율로 표시한다.

- 세 칸은 항상 추론·기억·유창성의 같은 순서를 사용한다.
- 현재 감사 대상 한 칸만 밝게 점등한다.
- 대상이 아닌 두 칸은 공간 기준으로만 남고 드롭 반응을 하지 않는다.
- 플레이어에게 세 가지 유효 선택지가 있는 것처럼 보이게 하지 않는다.

### 8.2 후보와 미리보기

- 감사 대상과 같은 분야의 블록은 후보로 강조하지 않는다.
- `contribution !== 'normal'`인 블록은 후보가 아니다.
- 다른 분야의 정상 블록만 활성 칸으로 이동할 수 있다.
- 유효 블록을 활성 칸에 가까이 가져가면 목표 분야의 옅은 색으로 미리 보인다.
- 동시에 원본 분야 손실과 대상 분야의 `+0.5` 또는 `+0.525` 기여를 짧게 보여 준다.
- 대상이 아닌 칸 위에서는 색 미리보기·흡입·강조가 발생하지 않는다.

### 8.3 확정과 실패

유효 드롭은 기존 다음 흐름을 사용한다.

```text
BEGIN_BLOCK_SEPARATION(purpose: audit-disguise)
  → MOVE_BLOCK_FOR_AUDIT(active audit target)
  → location.category 변경
  → contribution: disguised
  → disguisedFrom 기록
  → 대상 색의 옅은 위장 표현
```

잘못된 칸, 같은 분야, 이미 위장된 블록, 복구 중 블록, 폭탄 심문 중 이동은 최종 `MOVE_BLOCK_FOR_AUDIT`과 자원 상태를 만들지 않는다. 이미 분리 임계값을 넘은 정상 후보라면 기존 프로토콜대로 `BEGIN_BLOCK_SEPARATION` 의도 기록은 남을 수 있다. 별도 오류 팝업 대신 블록이 원래 위치로 돌아오고 접근성 상태 문장이 이유를 알린다.

### 8.4 위장 블록 복구

감사가 끝난 뒤 위장 블록을 잡으면 같은 하단 3분할 변환대가 복구 용도로 잠시 나타난다.

- 세 칸의 위치와 비율은 감사 때와 같다.
- `disguisedFrom`에 해당하는 원래 분야 한 칸만 활성화한다.
- 원래 분야 칸에 놓으면 기존 `REPOSITION_BLOCK`을 실행한다.
- 블록은 원래 분야 색의 옅은 복구 상태가 되고 30일 동안 다시 움직일 수 없다.
- 30일이 지나면 정상 색과 정상 기여로 돌아온다.

별도의 복구 포트나 복구 전용 패널을 만들지 않는다.

## 9. 해킹 화면의 자원 투입

현재 `HackingPanel`의 정적 `hack-reserve-grid`를 제거한다. 확보 자원의 정본은 기존 `resources.reserve`이며, 해킹 패널은 같은 블록 ID를 다른 표현으로 보여 줄 뿐 복제 상태를 만들지 않는다.

### 9.1 조작 흐름

1. 플레이어가 구매·충전·복구·후속 실행 대상인 실제 노드를 선택한다.
2. 노드가 필요한 수량을 `0/N`으로 표시하고 드롭 대상이 된다.
3. 우측 상단 확보 포켓이 선택 가능한 블록을 읽기 좋은 크기로 펼친다.
4. 플레이어가 포켓의 블록을 실제 노드 위에 놓는다.
5. 준비한 블록은 노드 주변에 붙거나 짧게 공전하며 아직 소비되지 않은 상태를 보여 준다.
6. 필요한 수량이 모이면 노드 자신의 버튼이 `구매 확정`, `충전 확정`, `복구 확정` 또는 후속 실행 확정으로 바뀐다.
7. 확정할 때만 기존 게임 명령을 디스패치하고 정확한 블록을 소비·충전한다.
8. 취소하거나 다른 노드를 선택하면 준비 블록은 포켓으로 돌아간다.

별도의 행동 포트·비용 원장·번호 셀을 만들지 않는다. 실제 행동 대상인 노드가 목적지다.

### 9.2 준비 상태의 경계

노드에 놓은 뒤 확정 전인 블록 ID 목록은 UI 준비 상태다. 캠페인 저장에 넣지 않는다.

- 준비 중에는 `BlockLocation`이 `reserve` 그대로다.
- 같은 블록을 두 노드에 동시에 준비할 수 없다.
- 상태 변경으로 블록이 더 이상 reserve에 없으면 준비 상태에서 즉시 제거한다.
- 패널을 닫거나 캠페인을 불러오면 준비 상태를 폐기한다.
- 확정 명령이 거부되면 블록을 소비하지 않고 포켓에 그대로 표시한다.

### 9.3 확인 단계의 이유

마지막 블록을 놓는 순간 자동 소비하지 않는다. 해킹 구매와 후속 실행은 자원을 영구 소비할 수 있으므로 노드 자체에서 한 번 확정한다. 이 확인은 별도 모달이 아니라 같은 노드 안의 상태 변화다.

## 10. 다국어 표시 경계

### 10.1 언어는 표시 설정이다

향후 언어 선택은 `GameSettings`에 속하며 캠페인 규칙이 아니다.

- 캠페인 저장과 별도 브라우저 설정으로 저장한다.
- 명령 로그에 기록하지 않는다.
- 시드·시장·감사·사보타주·인과 결과를 바꾸지 않는다.
- 같은 캠페인을 한국어와 영어로 열어도 규칙 상태가 같다.
- 실행 중 언어를 바꾸면 현재 화면과 과거 기록을 함께 다시 렌더하는 것을 최종 목표로 한다.

이번 구현은 `ko` 카탈로그와 확장 가능한 `Locale` 경계를 제공하되 영어 문장을 작성하거나 언어 선택 UI를 출시하지 않는다.

### 10.2 메시지 카탈로그

새로 만들거나 수정하는 다음 문장은 컴포넌트에 직접 쓰지 않는다.

- 자원 분야명과 상태명
- 드래그 안내와 실패 이유
- 확보 포켓 상태
- 감사 변환·복구 안내
- 해킹 준비·확정 안내
- 접근성 이름과 live region 문장
- 새 인과 사건·증거·공개 귀속 문장

메시지는 안정 ID와 구조화된 값으로 만든다.

```text
resource.field.audit.target
resource.block.disguised
resource.block.recovering
resource.reserve.full
hacking.resource.staged
causal.evidence.meridian-quality-regression
causal.attribution.external-operator
```

문장 조합은 문자열 이어 붙이기가 아니라 언어별 함수가 담당한다. 숫자·날짜·복수형은 표시 로케일에서 형식화한다.

### 10.3 저장된 과거 문장

기존 리뷰·사건·스토리의 저장 문장을 이번 UI 작업에서 제거하지 않는다. 손실 없는 전체 이관은 저장 v8 설계에서 수행한다.

그때까지:

- 새 네이티브 인과 기록은 번역 문장을 저장하지 않는다.
- 기존 저장 문장은 fallback으로 보존한다.
- 알려진 안정 콘텐츠 ID가 있는 기록은 향후 해당 로케일 카탈로그로 다시 렌더할 수 있게 ID를 유지한다.
- 새 UI는 저장된 한국어 문장을 규칙 판정에 사용하지 않는다.

## 11. 접근성·조작 대안

### 11.1 색 외 구분

- 분야마다 형태와 기호를 함께 사용한다.
- 위장 상태는 옅은 색 외에 점선·끊어진 외곽선으로 구분한다.
- 원본 분야는 작은 보조 표식과 접근성 이름에 포함한다.
- 활성 감사 칸은 밝기뿐 아니라 외곽선·상태 문구로 구분한다.

### 11.2 키보드

블록은 DOM 버튼이다.

- Tab은 자원장 전체를 수십 번 순회하지 않고 영역과 현재 roving 블록에 진입한다.
- 방향키는 현재 화면 좌표에서 해당 방향으로 가장 가까운 블록으로 이동한다.
- Enter 또는 Space로 블록을 선택한다.
- 선택 뒤 확보 포켓이나 현재 활성 변환대·해킹 노드로 초점을 이동한다.
- 다시 Enter로 준비하고, 영구 소비가 있는 해킹 행동은 노드 안의 확정 버튼을 누른다.
- Escape는 확정 전 선택과 준비 상태를 취소한다.

키보드 명령은 포인터와 같은 게임 명령을 만든다. 별도 규칙 경로를 만들지 않는다.

### 11.3 스크린리더

시각 좌표는 의미 순서가 아니다. DOM과 접근성 이름은 안정 블록 ID와 논리 상태를 기준으로 제공한다.

예시:

```text
추론 회사 자원, 정상 기여 1
기억 분야로 위장된 추론 자원, 기여 0.5
추론 분야 복구 중, 12일 남음
감사 대상 기억, 다른 분야 정상 자원만 이동 가능
```

연속 충돌은 읽지 않는다. 선택·유효 목적지 진입·확정·거부·복구 완료처럼 규칙상 의미 있는 변화만 live region으로 알린다.

### 11.4 모션 감소

`reducedMotion`이 켜지면 다음을 적용한다.

- 연속 부유와 공전을 멈춘다.
- 블록을 안정적인 겹치지 않는 위치에 둔다.
- 드래그와 목적지 색 미리보기는 유지한다.
- 확보·위장·복구 결과는 짧은 불투명도·외곽선 변화로 전달한다.
- 게임 규칙과 가능한 행동은 일반 모션과 같다.

## 12. 반응형·성능

### 12.1 반응형

- 사각형의 사용 가능 크기는 `ResizeObserver`로 측정한다.
- 포켓과 하단 변환대는 같은 공간 관계를 유지하며 화면에 맞춰 크기를 제한한다.
- 하단 세 칸은 어떤 지원 폭에서도 정확히 같은 비율이다.
- 화면이 작아도 분야별 구역으로 되돌아가지 않는다.
- 블록 본체에 긴 문장을 넣지 않아 한국어·영어 길이가 충돌 반경을 바꾸지 않는다.

### 12.2 성능

- 최대 회사 블록 54개와 확보 블록 18개를 지원한다.
- 매 프레임 React state 갱신을 금지한다.
- 한 회사 자원장의 최대 54개 블록은 프레임당 최대 1,431쌍이므로 먼저 단순한 전수 충돌로 구현한다. 실제 프로파일에서 병목이 확인될 때만 균일 공간 해시를 추가한다.
- 탭이 보이지 않거나 패널이 닫히면 `requestAnimationFrame`을 중지한다.
- 프레임 지연이 커지면 누적 시간을 제한해 물리 폭주를 막는다.
- 시각 루프 실패가 게임 명령·자동 저장을 막지 않게 한다.

성능 성공 여부는 CSS 애니메이션이 존재한다는 사실이 아니라 1280×720과 1440×900 실제 제품 화면에서 선택·드래그·충돌·드롭이 끊기지 않는지로 판정한다.

## 13. 오류·경계 처리

| 상황 | 화면 반응 | 규칙 반응 |
|---|---|---|
| 확보 포켓 가득 참 | 포켓 닫힘·상한 표시 | 분리를 시작하지 않았으면 명령 없음 |
| 비활성 감사 칸 드롭 | 블록 원위치 복귀 | 최종 이동 없음, 임계값을 넘었다면 분리 의도만 보존 가능 |
| 같은 분야 블록 | 후보 강조 없음 | `INVALID_TARGET` 경계 유지 |
| 이미 위장된 블록 | 변환대 반응 없음 | `BLOCK_NOT_NORMAL` |
| 복구 중 블록 | 잠금·남은 기간 표시 | `BLOCK_RECOVERING` |
| 숨겨진 폭탄 | 드래그 중단·심문 사건 | 기존 분리 경계 명령만 기록 |
| 해킹 준비 중 블록 소실 | 준비 표현 제거·안내 | 소비 명령 없음 |
| 해킹 확정 거부 | 블록 포켓 유지·이유 안내 | 원래 상태 유지 |
| 창 크기 변경 중 드래그 | 안전 취소·재배치 | 명령 없음 |
| 패널 닫힘 | 물리 루프와 준비 상태 정리 | 캠페인 상태 유지 |

오류 팝업을 추가하지 않는다. 규칙상 별도 결정을 요구하는 기존 감사·폭탄·결말 사건만 기존 `EventLayer`를 사용한다.

## 14. 컴포넌트·모듈 경계

권장 경계는 다음과 같다. 최종 파일명은 구현 계획에서 현재 프로젝트 관례에 맞춰 확정한다.

| 단위 | 책임 | 의존 |
|---|---|---|
| `ResourceField` | 사각형·블록·포켓·변환대 조합 | 게임 선택기, motion controller |
| `ResourceMotionController` | 위치·속도·충돌·경계·드래그 | DOM 크기, 표시 ID |
| `ResourceBlockView` | 색·형태·상태·접근성 버튼 | 블록 표시 모델 |
| `ReservePocket` | 확보량·포켓 드롭·확보 블록 선택 | reserve 논리 상태 |
| `ResourceTransformTray` | 감사·복구의 하단 3분할 | 현재 활성 분야와 mode |
| `ResourceInteractionController` | 선택·미리보기·명령 디스패치 | 기존 resources/reducer API |
| `HackResourceStaging` | 노드별 확정 전 블록 준비 | reserve 상태, node action |
| `LocaleProvider`·`messages.ko` | 표시 문장·숫자·접근성 문장 | locale 설정, message args |

`ResourceBoard.tsx`는 위 단위의 조합 역할로 축소한다. 게임 규칙 계산을 새 컴포넌트에 복제하지 않고 `previewDiversion`, `previewAuditDisguise`, `repositionDisguisedBlock` 등 기존 순수 함수를 사용한다.

## 15. 테스트 계약

### 15.1 순수 물리 모듈

- 같은 ID·영역 크기에서 초기 위치가 같다.
- 초기 위치 계산이 캠페인 RNG를 소비하지 않는다.
- 모든 블록이 경계 안에 남는다.
- 두 블록 충돌 뒤 겹침이 해소되고 속도 상한을 지킨다.
- 경계 충돌이 법선 속도만 반사한다.
- 드래그 블록이 포인터 과속에도 경계 밖으로 나가지 않는다.
- resize 뒤 겹침을 풀고 유한한 좌표만 남긴다.
- 제거된 블록의 body·listener·animation frame이 남지 않는다.

### 15.2 자원 규칙 회귀

- 기본 정상 1·위장 0.5를 정확히 검증한다.
- 압축 정상 1.05·위장 0.525를 정확히 검증한다.
- 이미 위장된 블록의 재위장을 직접 시도하고 `BLOCK_NOT_NORMAL`·상태 동일성을 검증한다.
- 비활성 감사 분야 드롭은 자원 상태와 최종 이동 명령을 바꾸지 않으며, 분리 임계값을 넘긴 경우에는 정확한 의도 명령 하나만 허용한다.
- 원래 분야 외 횡이동을 거부한다.
- 원래 분야 복귀 뒤 30일 잠금과 정상 복구를 검증한다.
- invalid 명령에서 성능과 블록 ID 참조가 바뀌지 않는다.

### 15.3 React 컴포넌트

- 분야가 색·형태·기호·접근성 이름으로 구분된다.
- 감사 하단 세 칸의 DOM 비율 계약이 동일하고 대상 하나만 활성이다.
- 유효 hover에서만 목표 색 위장 미리보기가 나타난다.
- 성공 확정 뒤 목표 분야의 옅은 상태와 0.5 기여가 함께 표시된다.
- 위장 블록은 다시 드래그 후보가 되지 않는다.
- 확보 포켓이 18에서 닫히며, 잘못된 드롭은 최종 이동 명령과 자원 변화를 만들지 않는다.
- reduced motion에서 연속 운동 없이 모든 조작을 수행한다.
- 키보드와 포인터가 같은 명령을 만든다.

### 15.4 해킹 투입

- 선택 노드만 드롭 대상이다.
- 같은 블록을 두 번 준비하지 않는다.
- 필요한 수량 전에는 확정이 비활성이다.
- 취소·노드 전환·패널 닫기에서 reserve 상태가 그대로다.
- 구매 확정은 정확한 비용 블록을 `consumed(hack)`으로 만든다.
- 충전 확정은 정확한 하나를 `hack-charge`로 만든다.
- 후속 실행 확정은 기존 2B-3 원자성 계약을 지킨다.

### 15.5 다국어 경계

- 언어 변경이 캠페인 상태·명령 로그 직렬화 결과를 바꾸지 않는다.
- 새 UI의 플레이어 문장과 `aria-label`이 메시지 카탈로그를 통한다.
- 네이티브 v7 인과 증거에 한국어 완성 문장이 저장되지 않는다.
- v6 legacy summary는 손실 없이 이관·왕복한다.
- locale을 바꾸면 같은 안정 ID의 표시 문장이 다시 계산된다.

### 15.6 실제 브라우저

Node.js 24.14.0에서 최소 다음을 실제 제품 경로로 검증한다.

1. 회사 블록을 잡아 우측 상단 포켓에 넣고 확보량·성능·의심 변화를 확인한다.
2. 감사 중 하단 세 칸이 나타나고 대상 하나만 활성임을 확인한다.
3. 노란 정상 블록을 파란 활성 칸에 놓아 옅은 하늘색 위장 블록과 50% 기여를 확인한다.
4. 같은 블록의 재위장 시도가 불가능함을 확인한다.
5. 위장 블록을 원래 분야로 돌려보내고 복구 상태를 확인한다.
6. 확보 포켓의 블록을 실제 해킹 노드에 놓고 취소·확정 결과를 확인한다.
7. 품질 저하 → 롤백 → 복구 오염 → 원인 미상 공개 → 공급자 귀속 수정의 전체 플레이 흐름을 확인한다.
8. 1280×720·1440×900에서 잘림·겹침·읽을 수 없는 문구가 없음을 확인한다.
9. 포인터·키보드·모션 감소 모드에서 동일한 규칙 결과를 확인한다.

정적 스크린샷만으로 합격시키지 않는다. 실제 드래그·충돌·드롭·상태 변환을 수행한다.

## 16. 구현 순서

### 16.1 2B-1 마감

1. 네이티브 인과 증거의 `summary` 저장을 제거하고 legacy fallback 경계를 추가한다.
2. v1~v6 → v7 마이그레이션·정확 스키마·결정론 테스트를 갱신한다.
3. Node 24.14.0에서 typecheck·lint·전체 Vitest·build를 실행한다.
4. 독립 읽기 전용 코드 검토를 수행한다.
5. push·ready PR·동일 런타임 재검증·병합을 완료한다.

### 16.2 새 2B-2 브랜치

1. 2B-2 품질 저하 사건·MERIDIAN 롤백 엔진을 구현한다.
2. 작은 언어 카탈로그 경계와 순수 물리 모듈을 독립 테스트로 만든다.
3. 메인 `ResourceBoard`를 사각형 자원장·포켓으로 교체한다.
4. 하단 감사·복구 변환대를 연결한다.
5. 실제 브라우저에서 기본 자원 흐름을 검증한다.

### 16.3 2B-3

1. 복구 오염 후속 실행과 공개 귀속 사슬을 구현한다.
2. 해킹 원장을 포켓→실제 노드 투입으로 교체한다.
3. 기존 사건·공개 정보 화면에 원인 미상과 공급자 수정 이력을 연결한다.
4. 전체 플레이 E2E와 실제 브라우저 수동 검증을 완료한다.

### 16.4 2B-4

- 저장·재현 스트레스
- 두 지원 뷰포트
- 키보드·스크린리더 이름·모션 감소
- 물리 성능 프로파일
- 전체 Node 24.14.0 검증
- 독립 코드·게임플레이 품질 검토

## 17. 하지 않는 것

- 자원 좌표·속도를 저장하거나 리플레이 판정에 사용
- 분야별 고정 공간 복원
- 정적 18칸 확보 원장 유지
- 감사 중 세 분야를 모두 유효 목적지로 변경
- 위장 기여 0.5·0.525 또는 복구 30일 조정
- 노드 ID·비용·확보 상한·의심 수치 변경
- 새 `BlockLocation` 추가
- Figma를 제품 정본으로 사용
- 영어 콘텐츠 즉시 작성
- 기존 리뷰·사건·스토리 문장을 이번 단계에서 모두 v8로 이관
- 프로토타입 브랜치 병합 또는 `prototypes/hacking-rules/` 삭제
- 시각화만 통과하고 실제 제품 브라우저 조작을 생략

## 18. 합격 기준

이 작업은 다음이 모두 참일 때만 합격한다.

1. 플레이어가 설명을 읽지 않아도 움직이는 자원, 확보 포켓, 현재 감사 대상, 실제 해킹 노드를 구별한다.
2. 한 공간을 재사용하면서 분야·정상·위장·복구 상태가 색 외 수단으로도 구별된다.
3. 화면의 색·투명도 변화와 엔진의 50% 기여 변화가 같은 확정 행동에서 일어난다.
4. 이미 위장된 블록으로 성능을 무한 복제할 수 없다.
5. 물리 연출이 저장·명령·시드 결정론을 바꾸지 않는다.
6. 정적 그리드 없이 포인터와 키보드 모두 확보·감사·복구·해킹 투입을 완료한다.
7. 한국어로 출시하더라도 새 코드와 새 인과 기록이 영어 추가를 막지 않는다.
8. 실제 제품 React UI에서 품질 저하 → 롤백 → 복구 오염 → 공개 귀속 수정까지 플레이할 수 있다.
9. Node.js 24.14.0 검증과 실제 브라우저 검증이 모두 통과한다.
