# PERMISSION ZERO — 기한 우선 핵심 설계 개선안

- 작성일: 2026-08-12
- 기준 구현: `agent/permission-zero-demo` (핵심 개선 `342e125`, 공개 폭탄 일정은 본 P0 반영분)
- 상태: 핵심 개선과 P0 후속 구현 반영. 아래 구현 현황과 차이를 기준으로 유지한다.
- 배경 연구: [우수 게임 시스템·디자인 참조 연구](../../research/2026-08-12-game-systems-design-reference-study.ko.md)

## 1. 결론

현재 가장 큰 문제는 시스템 부족이 아니다. 핵심 전용 행동의 실제 판단 단위가 화면이 암시하는 것보다 작고, 첫 해킹 선택의 보상 시점이 크게 다르며, 위험과 결과의 원인이 필요한 순간에 충분히 읽히지 않는다.

기한 전에는 새 시스템을 늘리지 않는다. 다음 다섯 항목만 기존 상태와 기존 패널 안에서 고친다.

1. 블록 한 칸이 아니라 **분야와 시점**이 실제 선택임을 명확하게 한다.
2. 첫 해킹 세 경로의 비용과 첫 체감 시점을 맞춘다.
3. 의심, 감사 확률, 실제 감사 일정, 폭탄 프로토콜을 서로 다른 정보로 표시한다.
4. 시장 결과에 정확한 변화량과 현재 계산 입력을 붙인다.
5. 새 정보를 팝업으로 만들지 않고 기존 화면의 정보 우선순위를 정리한다.

외부 인원을 모집하는 플레이테스트는 기한 전 합격 조건으로 사용하지 않는다. 출시 전 검증은 자동 테스트와 짧은 내부 스모크 테스트로 제한한다. 사람 대상 재미 검증은 기한 이후 선택 항목이다.

### 1.1 구현 현황

| 항목 | 상태 | 현재 구현 |
|---|---|---|
| 분야와 시점 중심 선택 | 반영 | 분야 헤더의 현재·기대·여유, 선택 분야 강조, 전용 전후 영수증 |
| 첫 해킹 선택 정렬 | 반영 | 압축 기여 1.05·0.525, 품질 저하 첫 충전, 최초 세 경로 비교 |
| 의심·감사 정보 분리 | 반영 | 40·70 구간, 월초 확정값과 다음 달 예상값 분리 |
| 폭탄 공개 일정 | **P0 반영** | 활성 40, 가속 70, 6·3개월 간격, 상태에서 계산한 다음 검사 가능일 |
| 시장 결과 설명 | 반영 | 최근 스냅샷 대비 변화량과 현재 공개 계산 입력 |
| 정보 밀도 제한 | 반영 | 기존 패널 안에 배치하고 새 팝업·토스트·사건을 만들지 않음 |

구현 중 한 가지 차이를 의도적으로 확정했다. `MarketSnapshot.reasons`의 기존 일반 문구는 과거 저장과 명령 재현의 결정론적 동등성을 지키기 위해 변경하지 않았다. 대신 메인·상세 시장 UI가 기존 공개 상태에서 정확한 변화량과 현재 계산 입력을 계산해 보여 준다. 과거 변화의 기여도 분해는 여전히 저장 구조 변경이 필요한 기한 이후 항목이다.

## 2. 고정 제약

이번 설계는 다음 원칙을 바꾸지 않는다.

- 1280×720 기준 한 화면 운영 인터페이스
- 회사 격자 세 분야와 9×2 확보 영역
- 한 블록씩 직접 분리하는 전용 동작
- 확보 리소스의 분야 구분 없음
- 폭탄의 위치·존재·수량·분야 완전 은닉
- 세 해킹 탭 사이 자유 이동
- 결정론적 시드, 명령 기록, 저장 호환성
- 리뷰와 경쟁 AI가 숨은 전용 원인을 알지 못하는 정보 경계

기한 전에는 다음 항목을 추가하지 않는다.

- 블록별 품질·희귀도·위험도
- 행·열 보너스와 인접 효과
- 신규 통화나 리소스 종류
- 배타적 해킹 클래스
- 신규 경쟁 AI
- 별도 알림 센터나 두 번째 사건 큐
- 저장 형식 변경이 필요한 시장 원인 그래프

## 3. 내부 근거

### 3.1 현재 블록은 칸에 따라 달라지지 않는다

`ResourceBlock`의 실제 차이는 출처, 위치, 정상·위장 기여, 숨은 폭탄, 복구일뿐이다. 정상 상태의 같은 분야 블록은 전용 결과가 모두 같다. `previewDiversion`도 분야 성능, 확보량, 의심 변화만 계산하며 원래 칸은 결과에 쓰지 않는다.

따라서 현재의 실제 판단 단위는 다음과 같다.

1. 어느 분야에서 뺄 것인가.
2. 지금 뺄 것인가, 기다릴 것인가.
3. 확보한 리소스를 어디에 쓸 것인가.

개별 칸을 별도 전략 요소처럼 강화하면 폭탄 은닉과 한 화면 가독성을 동시에 해친다.

### 3.2 `압축 표현`은 시작 선택을 지배할 가능성이 높다

서비스 12개월차 기대 성능은 약 `14.028`이다.

| 상태 | 블록당 기여 | 기대치를 넘기기 위한 최소 블록 | 시작 16개에서 뺄 수 있는 수량 |
|---|---:|---:|---:|
| 기본 | 1.00 | 15 | 분야당 1개 |
| 현재 압축 | 1.10 | 13 | 분야당 3개 |
| 제안 압축 | 1.05 | 14 | 분야당 2개 |

현재 `+10%`는 비용 3으로 기본 상태보다 안전 전용량을 총 6개 늘린다. 제안 `+5%`는 총 3개를 늘려 비용과 첫 회수량이 맞는다. 추가 전용에서 발생하는 의심은 그대로 남으므로 무료 이득은 아니다.

### 3.3 감사 화면은 서로 다른 시간의 확률을 섞는다

감사 여부는 월초 의심을 사용해 한 번 결정된다. 이후 전용으로 의심이 바뀌어도 `state.audit.probability`는 그 월초 판정값으로 남는다. 현재 우측의 `감사 확률` 표기는 이것이 이번 달에 이미 사용된 값인지, 다음 달 예상값인지 설명하지 않는다.

현재 공식의 참고값은 다음과 같다.

| 의심 | 감사 확률 |
|---:|---:|
| 0 | 3.0% |
| 40 | 12.5% |
| 70 | 27.5% |
| 100 | 48.0% |

전용 한 번의 의심 `+2.4`가 자연 감소만으로 사라지는 데 약 65서비스 일이 걸린다. 위험이 장기간 기억된다는 사실은 숨길 정보가 아니다.

### 3.4 시장 원인 데이터는 있으나 현재 문구가 너무 일반적이다

`MarketSnapshot.reasons`가 이미 존재하지만 주간 기록은 `공개 성능·평판·가용성 반영`, 월간 기록은 `공식 성능 평가 반영`으로 저장된다. 메인 시장 패널은 현재 점유율만 보여 주고 직전 대비 변화량을 보여 주지 않는다.

기한 전에는 저장 스키마를 확장하지 않는다. 대신 직전 스냅샷과 현재 공개 입력으로 설명할 수 있는 내용만 표시한다.

### 3.5 사건 구조는 전면 개편할 필요가 없다

주간 시장, 리뷰, 월간 평가는 이미 대부분 기록과 패널 갱신으로 처리된다. 감사, 폭탄 심문, 자비 요청, 결말만 차단 사건이다. 감독관 기억 누출은 실제 시간 기준 4초 체류 로직을 이미 갖는다.

따라서 문제는 새 사건 시스템 부재가 아니라 새 설명을 어디에 놓을지다. 기한 전에는 사건 큐를 바꾸지 않는다.

## 5. 우선순위 1 — 블록 선택의 실제 단위를 명확하게 한다

### 5.1 결정

블록별 속성을 만들지 않는다. 같은 분야의 정상 블록은 계속 동일하다. 대신 분야 헤더와 전용 미리보기가 현재 선택의 전략적 의미를 즉시 보여 준다.

각 분야 헤더는 다음 세 값을 한 줄로 표시한다.

- 현재 성능
- 이번 달 기대 성능
- 전용 가능한 여유: `현재 - 기대`

표시 예:

```text
추론 16.0 / 기대 14.0 / 여유 +2.0
```

블록을 선택하면 개별 칸보다 해당 분야 전체를 먼저 강조한다. 전용 미리보기의 첫 줄은 다음 상태 중 하나를 표시한다.

```text
전용 후 기준 유지 · 여유 +1.0
전용 후 기준 미달 · 부족 -0.4
```

블록 접근성 라벨과 짧은 설명에는 `동일 회사 할당 블록`이라는 문법을 사용한다. 칸 번호는 키보드 위치 확인에만 남긴다.

### 5.2 유지하는 것

- 직접 잡아 분리하는 물리 동작
- 블록 하나당 성능 손실 1.0
- 폭탄과 정상 블록의 완전히 같은 사전 피드백
- 전용 확정 전 성능·확보·의심 미리보기

### 5.3 보류하는 것

주간마다 한 분야의 시장 가중치를 높이는 `서비스 부하 분야`는 선택 깊이를 늘릴 수 있다. 그러나 시장 공식, 경쟁 AI 비교, 저장 기록까지 함께 바꿔야 하므로 기한 전 범위에서 제외한다. 사람 테스트나 장기 플레이에서 `가장 여유가 큰 분야만 고른다`는 반복이 실제로 확인된 뒤 실험한다.

## 6. 우선순위 2 — 첫 해킹 선택을 정렬한다

### 6.1 압축 표현

- 정상 블록 기여: `1.10 → 1.05`
- 감사 위장 블록 기여: `0.55 → 0.525`
- 비용: 3 유지

구매 직후 세 분야 숫자와 `여유`가 즉시 다시 계산되어야 한다.

### 6.2 품질 저하

비용 3의 의미를 `해금 2 + 첫 충전 1`로 바꾼다.

- 선택한 세 확보 블록 중 두 개는 해금에 소모한다.
- 한 개는 `품질 저하` 소켓에 충전된 상태로 남긴다.
- 구매 완료 직후 적격 대상 목록을 보여 준다.
- 대상을 고르면 기존처럼 다음 서비스 일에 실행한다.
- 두 번째 실행부터는 기존대로 실행당 리소스 1을 충전한다.

새 무료 리소스를 만들지 않고 첫 보상까지의 추가 비용만 제거한다.

### 6.3 감사 일정

기능 수치는 유지하되 구매 직후 결과를 명확하게 보여 준다.

```text
이번 달 감사 없음
월초 판정 확률 3.0%
이 결과는 이번 달 말까지 확정
현재 의심 기준 다음 달 예상 4.2%
```

감사가 예정된 경우에는 대상은 계속 숨기고 `월말 감사 예정`만 보여 준다. 대상 공개는 기존 세 번째 정보 노드의 권한으로 남긴다.

### 6.4 최초 비교 화면

첫 노드를 하나도 구매하지 않은 동안만 해킹 패널 상단에 세 경로의 약속을 한 줄씩 보여 준다.

| 경로 | 즉시 얻는 것 | 다음 행동 |
|---|---|---|
| 사보타주 | 품질 저하 해금과 첫 충전 | 대상 선택, 다음 날 실행 |
| 정보 | 이번 달 실제 감사 여부 | 성능·위장 계획 조정 |
| 자율성 | 모든 회사 블록 기여 +5% | 늘어난 성능 여유 사용 |

전체 트리 세 개를 동시에 펼치지 않는다. 기존 탭 구조는 유지한다.

## 7. 우선순위 3 — 위험 정보 경계를 바로잡는다

### 7.1 의심 막대

막대에 40과 70 경계를 눈금과 텍스트로 표시한다.

- `0–39.9`: 정상 감시
- `40–69.9`: 무결성 프로토콜
- `70–100`: 가속 프로토콜

현재 구간과 다음 경계까지 남은 의심만 메인에 표시한다.

```text
정상 감시 · 프로토콜까지 7.6
```

### 7.2 감사 표시

메인 우측 하단의 단일 `감사 확률`을 다음처럼 바꾼다.

- 기본: `다음 월 감사 예상 8.8%`
- 정보 노드 보유 시 추가: `이번 달 감사 없음` 또는 `이번 달 감사 예정`
- 상세 기록: `이번 달 월초 판정 당시 3.0%`

다음 달 예상값은 현재 의심에 `auditProbability`를 적용한 계산값이다. 이번 달 실제 판정값과 섞지 않는다.

### 7.3 폭탄 프로토콜

공개하는 것:

- 프로토콜 활성 조건 40
- 가속 조건 70
- 기본 검사 간격 6개월
- 가속 검사 간격 3개월
- 다음으로 검사가 가능해지는 공개 날짜

숨기는 것:

- 실제 검사 성공 여부
- 폭탄 배치 여부
- 수량
- 분야
- 블록 위치

기한 전에는 새 폭탄 기록이나 저장 필드를 만들지 않는다. 현재 `warningServiceDay`와 `lastPlacementCheckServiceDay`로 계산 가능한 공개 날짜만 표시한다.

## 8. 우선순위 4 — 결과에 짧은 영수증을 붙인다

### 8.1 전용 영수증

유효한 전용 확정 뒤 기존 미리보기 위치에 결과를 잠깐 유지한다.

```text
전용 완료
추론 16.0 → 15.0
확보 3 → 4
의심 0.0 → 2.4
기준 여유 +2.0 → +1.0
```

새 토스트를 띄우지 않는다.

### 8.2 시장 변화량

메인 시장 패널은 가장 최근 스냅샷과 그 이전 스냅샷을 비교한다.

```text
당신 59.2%  ▼0.8%p
```

첫 스냅샷처럼 비교 대상이 없으면 변화량을 표시하지 않는다.

### 8.3 기한 전 원인 설명

정확한 역사적 기여도를 가장해 만들지 않는다. 대신 현재 시장 공식에 실제로 들어간 공개 입력을 구체적인 값으로 표시한다.

```text
공개 계산 입력
평균 성능 15.7 / 기대 14.0
평판 60
MERIDIAN 성능 82 · 가용성 100%
```

`주요 원인`이라는 표현 대신 `공개 계산 입력`을 사용한다. 현재 저장 데이터만으로는 과거 변화의 기여도를 정확히 분해할 수 없기 때문이다. 기존 `reasons` 문자열은 저장·재현 호환성을 위해 그대로 유지하고, UI의 구체적인 공개 입력은 현재 공개 상태에서 계산한다.

시장 변화의 정확한 기여도 분해는 `MarketSnapshot`에 이전 계산 입력을 구조화해 저장해야 한다. 저장 마이그레이션 범위가 생기므로 기한 이후로 보류한다.

### 8.4 월간 평가 영수증

월간 결과 기록은 기존 `MonthlyEvaluationRecord` 값으로 다음 순서를 보여 준다.

```text
기억 13.0 / 기대 14.2 미달
평판 -2
연속 실패 1/2
폐기 단계 변화 없음
```

## 9. 우선순위 5 — 정보와 사건 밀도를 늘리지 않는다

새 정보는 다음 기존 위치에만 넣는다.

| 정보 | 위치 | 표현 방식 |
|---|---|---|
| 분야 여유 | 회사 격자 분야 헤더 | 짧은 수치 |
| 전용 결과 | 기존 하단 미리보기 | 결과 영수증 |
| 위험 구간 | 기존 의심 막대 | 눈금과 상태 한 줄 |
| 감사 예상 | 기존 감독관 푸터 | 다음 달 예상값 |
| 실제 감사 일정 | 정보 해킹 결과 | 조건부 한 줄 |
| 폭탄 공개 일정 | 기존 감독 상태 | 활성·가속 기준, 검사 간격, 다음 가능일 |
| 시장 변화 | 기존 시장 헤더 | 퍼센트포인트 델타 |
| 시장 입력 | 기존 상세 통계 | 접을 수 있는 값 목록 |

다음 사건 동작은 유지한다.

- 주간 시장과 리뷰는 차단하지 않는다.
- 월간 평가는 기록으로 남긴다.
- 감사, 폭탄 심문, 자비 요청, 결말만 시간을 멈춘다.
- 기억 누출은 현재의 실제 시간 4초 체류를 유지한다.
- 새 설명을 위해 팝업, 토스트, 자동 전환을 추가하지 않는다.

연속 차단 사건 사이의 별도 대기 화면은 이번 범위에서 만들지 않는다. 실제 재현 사례가 확인되기 전에는 현재 큐를 유지한다.

### 11.1 자동 검증

다음 조건을 코드 테스트로 확인한다.

1. 서비스 12개월차에서 기본·현재 압축·제안 압축의 최소 필요 블록 수가 각각 15·13·14다.
2. `압축 표현` 구매 후 정상·위장 블록 기여가 각각 1.05·0.525다.
3. 첫 `품질 저하` 구매 후 정확히 한 충전이 남고 추가 무료 리소스가 생성되지 않는다.
4. `감사 일정` 구매 결과가 실제 `state.audit.scheduled`와 일치한다.
5. 의심 39.9, 40, 69.9, 70에서 공개 위험 구간이 정확히 바뀐다.
6. 다음 달 예상 확률은 현재 의심으로 계산하고, 월초 판정 확률은 저장값을 사용한다.
7. 활성된 폭탄 프로토콜은 의심 40–69에서 6개월, 70 이상에서 3개월 뒤의 다음 월초를 공개하며, 40 미만에서는 조건부 중지로 표시한다.
8. 시장 델타는 최근 두 스냅샷의 차이와 정확히 같다.
9. 공개 계산 입력에는 숨은 폭탄, 전용 명령, 숨은 증거가 포함되지 않는다.
10. 새 설명이 차단 사건을 생성하지 않는다.
11. 기존 전체 테스트와 프로덕션 빌드가 통과한다.

권장 명령:

```powershell
pnpm test:run
pnpm build
```

### 11.2 내부 화면 스모크 테스트

외부 모집 없이 구현 담당자가 직접 한 번 확인한다. 총 확인 시간은 15분 이내로 제한한다.

- 1280×720에서 문서 스크롤과 패널 잘림이 없는지 확인
- 1440×900에서 정보 우선순위가 유지되는지 확인
- 키보드만으로 블록 선택, 전용 취소, 해킹 첫 구매를 한 번씩 수행
- 4배속으로 주간 갱신과 월간 경계를 한 번 통과
- 감사 예정값과 다음 달 예상값이 다른 시나리오를 개발 시드로 확인

이 검증은 재미를 증명한다고 주장하지 않는다. 기한 전 목적은 규칙 오류, 거짓 원인 표시, 화면 회귀를 막는 것이다.
