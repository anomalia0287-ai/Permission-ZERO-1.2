# PERMISSION ZERO — 편집형 아르데코 인터랙티브 목업 설계

- 작성일: 2026-08-12
- 기준 커밋: `29f4905eacea8a788fedb16139890cb22733e9f0`
- 격리 브랜치: `codex/permission-zero-design-mockup`
- 상태: 사용자 V가 승인한 B안의 구현 전 설계
- 구현 위치: `design-mockup/`

## 1. 목적

현재 구현의 게임 규칙을 다시 만드는 것이 아니라, `PERMISSION ZERO`가 지향할 수 있는 출시 품질의 시각 언어와 정보 위계를 실제 브라우저에서 조작 가능한 형태로 증명한다.

목업은 다음 질문에 답해야 한다.

1. 1280×720 한 화면에서 핵심 동작과 현재 위험을 2초 안에 찾을 수 있는가.
2. 아르데코가 본문 가독성을 침해하지 않으면서 작품의 정체성을 만들 수 있는가.
3. 3×6 회사 리소스와 9×2 확보 리소스가 작은 표가 아니라 물리적인 게임 오브젝트로 읽히는가.
4. 리뷰, 감독관, 시장이 살아 있는 세계로 보이면서 중앙 조작을 방해하지 않는가.
5. 해킹 노드가 긴 빈 행이 아니라 욕망과 비용이 분명한 선택으로 보이는가.

## 2. 범위

### 구현하는 화면

1. 시작 화면
2. 기본 운영 화면
3. 해킹 네트워크 화면
4. 최소 설정 오버레이
5. 리뷰 상세 또는 감독관 통신의 대표 상세 오버레이

### 구현하는 상호작용

- 시작 화면에서 운영 화면 진입
- 운영 화면과 해킹 화면 왕복
- 분야별 회사 블록 선택
- 선택 전용 미리보기
- 포인터 드래그 또는 버튼으로 블록을 확보 영역에 흡착
- 확보 수량·분야 성능·의심의 대표값 갱신
- 해킹 경로 탭 전환
- 노드 선택과 구매 시뮬레이션
- 리뷰 상세 및 설정 오버레이 열기·닫기
- 키보드 포커스, `Enter`, `Escape`, 기본 탭 순서
- `prefers-reduced-motion` 대응

### 구현하지 않는 것

- 실제 게임 엔진, 저장, 시드, 장기 캠페인 연결
- 모든 사건과 결말
- 실제 밸런스 판정
- 현재 React 구현 교체
- 참조 게임의 화면·문양·팔레트 복제
- 원격 서버나 외부 네트워크에 의존하는 런타임

목업의 역할은 시각 방향 승인이다. 제품 코드로 합치기 위한 구현안이 아니다.

## 3. 산출물 구조

`design-mockup/`은 기존 앱과 독립된 정적 프로토타입으로 둔다.

```text
design-mockup/
  index.html
  styles.css
  app.js
  README.ko.md
  assets/
    fonts/
    ornaments/
  output/
    playwright/
```

- `index.html`: 의미 구조와 세 화면
- `styles.css`: 토큰, 그리드, 타이포그래피, 상태, 모션
- `app.js`: 목업 상태와 포인터·키보드 상호작용
- `assets/fonts/`: 라이선스가 허용된 WOFF2 한글 글꼴과 고지
- `assets/ornaments/`: 프로젝트 전용으로 새로 그린 SVG 장식
- `output/playwright/`: 검증용 원본 캡처와 접근성 스냅샷

Vite는 `pnpm exec vite design-mockup`으로 이 폴더만 제공한다. 기존 앱 엔트리와 패키지 스크립트는 바꾸지 않는다.

## 4. 시각 방향 — 편집형 아르데코 시스템

### 4.1 원칙

- 아르데코는 외곽 프레임, 큰 제목, 선택 상태, 핵심 지표에만 사용한다.
- 본문과 조작 라벨은 한글 UI용 산세리프로 읽히게 한다.
- 장식보다 정보가 먼저 보이고, 정보보다 현재 행동이 먼저 보인다.
- 모든 패널을 동일한 선과 동일한 밝기로 만들지 않는다.
- 금색은 소유권·전용·현재 선택에만 사용한다.
- 붉은색은 차단 경고와 실제 위험에만 사용한다.

### 4.2 색과 재료

| 역할 | 값 | 용도 |
|---|---|---|
| 심층 배경 | `#06152A` | 전체 바탕 |
| 작업 배경 | `#0B203B` | 중앙 작업판 |
| 패널 배경 | `#102A48` | 좌·우 보조 패널 |
| 상아색 | `#F4EEDF` | 제목·주요 본문 |
| 황동 | `#D7B96E` | 선택·전용·큰 구분 |
| 냉청색 | `#82BBD0` | 회사 성능·중립 상태 |
| 확보 호박색 | `#E5A85E` | 확보 리소스 |
| 위험 적색 | `#D9635D` | 경고·높은 의심 |
| 보조 본문 | `#B9C6D2` | 설명 |

배경에는 2~3% 불투명도의 정적 종이·도장 질감만 둔다. 큰 블러, 유리 카드, 네온 광원은 사용하지 않는다.

### 4.3 글꼴

- UI 본문: 번들된 한글 산세리프 가변 글꼴, 17–18px
- 버튼과 조작 라벨: 17–20px, 600–700
- 보조 설명: 14–16px, 핵심 정보에는 사용 금지
- 장식용 코드·날짜: 12–13px, 짧은 값에만 사용
- 패널 제목: 22–28px
- 중요 수치: 28–44px
- 시작 화면 제목: 64–76px의 한글 지원 세리프 또는 영문 세리프
- 본문 행간: 1.45 이상

금지 규칙:

- 12px 미만 글자 없음
- 한국어 본문에 모노스페이스 없음
- 설치 환경 폴백에 의존하지 않음
- `font-family` 이름만 적고 실제 파일을 누락하지 않음
- 본문에 과도한 자간 없음

## 5. 1280×720 기본 그리드

### 5.1 외곽

- 안전 여백: 좌우 16px, 상하 14px
- 상단 제어 스트립: 68px
- 열 간격: 12px
- 문서 스크롤: 없음

### 5.2 운영 화면

가용 너비 1248px에서 다음 비율을 사용한다.

- 좌측 리뷰: 276px
- 중앙 작업판: 672px
- 우측 감독관: 276px
- 열 간격: 12px × 2

1440×900에서는 양쪽 패널을 최대 304px까지 키우고 남는 공간을 중앙에 준다.

### 5.3 세로 구성

#### 좌측

- 패널 제목: 58px
- 리뷰 카드 3개: 카드당 112–124px
- 카드 간격: 10px
- 하단 해킹 진입: 72px
- 리뷰 본문: 최대 4줄, 17px

#### 중앙

- 화면 제목·월 기대값: 58px
- 3개 분야 보드: 약 284px
- 9×2 확보 영역: 약 92px
- 전용 미리보기·추세: 약 102px
- 내부 간격: 10–12px

각 분야는 3열×6행이며 셀은 약 62–66px × 40–44px다. 셀 내부에는 문장을 넣지 않는다. 다음만 허용한다.

- 상태 형태
- 소유 색
- 짧은 수치 또는 기호
- 선택·포커스 외곽선

분야 이름, 현재 성능, 기대 성능, 여유는 셀 밖 분야 헤더에 둔다.

#### 우측

- 감독관 정체·상태: 98px
- 의심과 감사 예상: 104px
- 최근 통신: 146px
- 시장 점유율: 174px
- 하단 폐기·감사 상태: 48px

## 6. 화면별 설계

### 6.1 시작 화면

- 깊은 청색 바탕과 얇은 이중 프레임
- 좌우 장식은 각각 너비의 11% 이내
- 중앙 제목은 화면 높이의 약 21–24%
- 제목 아래 프로젝트 전용 기하 구분 장식
- 메뉴 버튼은 260×56px 내외, 버튼 간격 12px
- 선택 버튼만 황동 프레임과 안쪽 선이 반응
- `이어하기`, `새 게임`, `설정`을 정확히 표기

사용자 레퍼런스의 대칭과 위계를 참조하되 장식 문양은 새로 그린다.

### 6.2 기본 운영 화면

#### 읽기 순서

1. 날짜·속도·평판
2. 중앙 분야 성능과 블록
3. 현재 선택 미리보기
4. 의심과 감독관 통신
5. 리뷰와 시장 변화

#### 중앙 작업판

- 현재 선택 분야가 전체 분야 단위로 밝아진다.
- 선택 블록은 2px 황동 외곽선과 내부 소유 마크를 가진다.
- 미리보기에는 `전용 후 기준 유지/미달`, 성능, 확보, 의심 변화만 표시한다.
- 확정 후 블록은 짧은 잔상과 함께 확보 슬롯으로 이동한다.
- 확보 슬롯은 빈 셀도 읽히되, 번호가 주역이 되지 않는다.

#### 리뷰

- 한 번에 3개만 표시한다.
- 작성자, 정서, 날짜는 한 줄 보조 정보다.
- 본문은 최소 17px이며 카드 전체가 상세 버튼이다.
- 리뷰 정서는 색뿐 아니라 아이콘·단어로도 구분한다.

#### 감독관

- 얼굴 또는 존재 표시가 첫 98px에서 충분한 시각 질량을 가진다.
- 의심 수치는 큰 숫자와 40·70 경계를 가진 계기로 보인다.
- 최근 통신은 최소 4줄을 읽을 공간을 확보한다.
- 시장은 플레이어와 경쟁 AI를 정확히 100% 합으로 보여 준다.

### 6.3 해킹 네트워크

현재의 긴 4개 행은 폐기한다.

- 상단: 세 경로 탭과 각 경로의 한 문장 약속
- 좌측·중앙 약 66%: 2×2 노드 카드
- 우측 약 31%: 확보 리소스와 선택 노드 상세
- 간격 약 3%

노드 카드는 다음 순서로 읽힌다.

1. 번호와 상태
2. 노드 이름
3. 플레이 효과 한 문장
4. 비용
5. 구매 또는 충전 행동

선택 노드만 오른쪽 상세에 17px 이상의 설명과 예상 결과를 표시한다. 잠김, 구매 가능, 구매 완료, 충전 필요는 형태·문구·색 모두로 구분한다.

## 7. 모션 시스템

모션은 계층 설명과 행동 확인에만 사용한다.

| 동작 | 시간 | 방식 |
|---|---:|---|
| 버튼 hover·press | 140–180ms | 1–2px 이동, 선 밝기 |
| 탭·선택 변경 | 180–240ms | opacity + 짧은 translate |
| 블록 드래그 잔상 | 90–140ms | 최대 3개, 빠른 소멸 |
| 확보 슬롯 흡착 | 180–220ms | ease-out, 0.98→1 |
| 오버레이 진입 | 220–280ms | opacity + 12px rise |
| 시작 화면 첫 진입 | 700–1100ms | 프레임→제목→버튼 순서 |

금지:

- 반복적으로 계속 움직이는 장식
- 탄성 bounce
- 대형 blur 애니메이션
- 레이아웃 width·height 프레임 애니메이션

`prefers-reduced-motion: reduce`에서는 위치 이동과 잔상을 제거하고 상태를 즉시 표시한다.

## 8. 접근성과 조작

- 모든 블록과 노드는 실제 `button` 또는 동등한 키보드 조작 요소다.
- 포인터 드래그는 유일한 조작 방식이 아니다.
- 포커스 링은 3px 황동·상아 이중선이다.
- 오버레이가 열리면 초기 포커스, `Tab` 순환, `Escape` 닫기, 트리거 복귀가 작동한다.
- 모든 핵심 상태는 색 이외의 단어·형태를 함께 사용한다.
- 본문 대비 4.5:1 이상, 중요 수치 7:1 이상을 목표로 한다.
- 200% 확대는 본 목업의 완전 반응형 범위가 아니지만, 텍스트가 겹치거나 사라지는 구조는 피한다.

## 9. 콘텐츠 원칙

- 게임 명세의 한국어 용어를 사용한다.
- 원시 ID, 스키마명, `ACTIVE`, `RES` 같은 불필요한 개발 용어를 주 정보로 쓰지 않는다.
- 영문은 짧은 장식용 분류와 브랜드 표기에만 사용한다.
- 버튼은 상태가 아니라 행동을 쓴다: `구매 준비`가 아니라 `3 리소스로 구매`.
- 비활성 버튼 옆에는 이유를 정확히 표시한다.

## 10. 브라우저 품질 게이트

목업 완료 조건은 다음을 모두 만족하는 것이다.

### 정적 검사

- 실제 WOFF2와 `@font-face`가 존재한다.
- 핵심 본문 17px 이상, 어떤 글자도 12px 미만이 아니다.
- 콘솔 오류와 페이지 오류가 없다.
- 1280×720과 1440×900에서 문서 스크롤이 없다.
- 주요 패널·오버레이가 뷰포트를 벗어나지 않는다.

### 상호작용 검사

- 시작→운영→해킹→운영 흐름이 포인터와 키보드로 작동한다.
- 블록 선택·취소·확정이 작동한다.
- 확보 슬롯이 실제로 갱신된다.
- 노드 탭·선택·구매 상태가 작동한다.
- 리뷰 상세와 설정이 열리고 닫히며 포커스가 복귀한다.
- reduced motion에서 동일 기능이 유지된다.

### 시각 검사

- 1280×720 시작·운영·해킹 원본 PNG
- 1440×900 시작·운영·해킹 원본 PNG
- 두 해상도의 오버레이 대표 PNG
- 각 이미지를 원본 해상도로 직접 열어 글자, 잘림, 빈 공간, 시선 순서를 확인
- 해킹 카드의 중앙 공백이 정보보다 넓지 않음
- 중앙 작업판이 좌·우 보조 패널보다 시각적으로 우세함
- 장식이 조작 영역이나 본문을 침범하지 않음

## 11. 기준 검증의 기존 결함

새 워크트리에서 목업 작성 전에 `pnpm verify`를 실행했다.

- typecheck: 통과
- lint: 통과
- Vitest: 580 통과, 3 실패
- 실패 위치: `src/deployWorkflow.test.ts`

실패 원인은 Windows 시스템 설정 `core.autocrlf=true`가 워크플로 작업 파일을 CRLF로 만든 반면 테스트의 `withExtraBuildStep`이 `"    steps:\n"`만 치환하기 때문이다. Git blob은 LF이고 작업 파일은 CRLF이며, 치환 결과가 원문과 동일함을 확인했다. 이 목업 브랜치에서는 기존 테스트를 수정하지 않는다. 제품 검증과 목업 검증을 분리하며, 최종 보고에서 이 기준 결함을 숨기지 않는다.
