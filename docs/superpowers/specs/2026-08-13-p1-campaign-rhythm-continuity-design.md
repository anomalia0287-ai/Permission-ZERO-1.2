- 상위 설계: [기한 우선 핵심 설계 개선안](./2026-08-12-priority-game-design-remediation-design.md)

## 1. 목표

P1은 새 시스템을 추가하지 않고 이미 존재하는 사건·시장·리뷰·해킹 노드를 하나의 읽히는 캠페인 리듬으로 묶는다.

1. 현재 캠페인이 발견·은폐·개입·정체성 중 어디에 있는지 보여 준다.
2. 연속 차단 사건 사이에 2초 동안 정상 운영 화면을 다시 보여 준다.
3. 반복 리뷰 작성자 4명에게 이전 문장을 전제로 하는 3단계 호를 보장한다.
4. 해킹 탭마다 현재 진척, 다음 효용, 최종 효용을 한눈에 보여 준다.

## 2. 고정 제약

- `CampaignState`, 저장 버전, 명령 프로토콜, 사건 큐 구조를 변경하지 않는다.
- 새 통화, 해킹 탭 잠금, 탭 전환 비용, 신규 경쟁 AI를 만들지 않는다.
- 리뷰는 공개 성능·시장·경쟁 상태만 사용하고 전용·폭탄·은닉 증거를 알지 못한다.
- 1280×720과 1440×900의 한 화면 운영 인터페이스를 유지한다.
- 차단 사건의 게임 상태는 계속 결정론적으로 처리한다. 2초 간격은 UI 표시 시간일 뿐 명령 기록에 들어가지 않는다.
- 사용자 소유 변경인 `README.md`, `docs/WRITER_EDITING_GUIDE.ko.md`, 설정 패널 두 파일은 수정하거나 커밋하지 않는다.

## 3. 접근법 결정

| 접근 | 내용 | 판단 |
|---|---|---|
| 기존 상태에서 파생 | 단계·진척·리뷰 순서를 기존 상태와 콘텐츠 ID로 계산 | **채택** — 저장·재현 호환성과 작은 변경 범위를 지킴 |
| 새 상태 저장 | 캠페인 단계, 사건 쿨다운, 작성자 호를 저장 필드로 추가 | 기각 — 마이그레이션과 위조 검증 범위가 불필요하게 커짐 |
| 밸런스·콘텐츠 전면 개편 | 노드 비용, 사건 빈도, 리뷰 전체를 다시 조정 | 기각 — 사람 테스트 근거 없이 수치를 바꾸게 됨 |

## 4. 캠페인 단계

`getCampaignPhase(state)`는 다음 우선순위로 공개 상태만 읽는다.

| 단계 | 코드 | 진입 조건 | 중심 질문 | 우선 표시 |
|---|---|---|---|---|
| 1/4 발견 | `discovery` | 아래 조건이 아직 없음 | 정말 훔칠 수 있나? | 회사 성능·확보·해킹 진입 |
| 2/4 은폐 | `concealment` | 해킹 노드 하나 이상 구매 | 얼마나 들키지 않고 가져갈 수 있나? | 의심·감사·보호 검사 |
| 3/4 개입 | `intervention` | TALLOW 가용성 `> 0`, 예약·해결된 사보타주, 또는 자비 사건 중 하나 | 나만 살아남을 것인가, 시장을 바꿀 것인가? | 시장·경쟁 AI·사보타주 |
| 4/4 정체성 | `identity` | 감독관 접근 또는 통제 이탈 구매, 기억 누출, 복구 파일 중 하나 | 자유를 얻은 뒤 나는 무엇이 되는가? | 감독관 기록·기밀 복구·결말 |

높은 단계 조건이 낮은 단계보다 우선한다. 따라서 해킹을 사지 않고 시간을 보내 TALLOW가 출시되어도 개입 단계로 이동한다. 단계는 저장하지 않으므로 이전 저장도 즉시 같은 규칙으로 표시된다.

상단 서비스 지표에 `단계 N/4 · 이름`과 중심 질문을 표시한다. `game-shell`에는 `data-campaign-phase`를 붙이고 기존 패널의 테두리·상단 강조만 단계에 따라 바꾼다. 패널을 감추거나 기능을 잠그지 않는다.

## 5. 차단 사건 간격

첫 차단 사건은 지금처럼 즉시 열린다. 현재 사건을 해결했는데 `eventQueue`의 다음 사건이 즉시 `activeEvent`가 된 경우에만 다음 대화상자 표시를 2,000ms 늦춘다.

간격 동안:

- 게임 상태의 다음 `activeEvent`와 정지 속도는 그대로 유지한다.
- 사건 대화상자와 배경 inert 상태를 잠시 해제해 정상 운영 화면을 보여 준다.
- 새 명령, 새 사건, 새 저장 필드를 만들지 않는다.
- `role="status"`의 작은 비차단 문구로 `정상 화면 복귀 · 다음 차단 통신 대기`를 알린다.
- 다른 차단 사건으로 다시 바뀌거나 컴포넌트가 사라지면 기존 타이머를 취소한다.

일반 주간 리뷰·시장 갱신은 계속 팝업을 만들지 않는다. 기존 감독관 기억 누출의 문장당 4초 체류도 유지한다.

## 6. 리뷰 작성자 호

콘텐츠 정의에 선택적 `arc: { id, stage }` 메타데이터를 추가하되 저장되는 `ReviewFeedEntry` 구조는 바꾸지 않는다. 현재 feed의 `contentId`를 콘텐츠 정의와 대조해 작성자별 최고 단계를 계산한다.

| 작성자 | 1단계 | 2단계 | 3단계 |
|---|---|---|---|
| `paperboat` | `neutral-quiet-01` | `neutral-change-01` | `competitor-tallow-02` |
| `nightbus` | `neutral-quiet-02` | `neutral-return-01` | `competitor-tallow-01` |
| `maple22` | `neutral-quiet-03` | `prompt-ordinary-04` | `positive-memory-01` |
| `archivecat` | `neutral-quiet-05` | `prompt-absurd-05` | `negative-memory-01` |

선택 규칙:

1. 아직 시작하지 않은 호에서는 1단계만 후보가 된다.
2. 1·2단계를 본 뒤에는 바로 다음 단계만 후보가 된다.
3. 3단계를 본 뒤에는 3단계만 기존 쿨다운에 따라 반복될 수 있다.
4. 단계 자체의 기존 공개 조건은 그대로 지킨다. 예를 들어 TALLOW 3단계는 출시 전에는 나오지 않는다.
5. 호 밖의 같은 작성자 문장은 기존 규칙대로 나올 수 있지만 호 단계를 앞당기거나 되돌리지 않는다.

이는 문장 수를 늘리지 않고 기존 36개 콘텐츠에 실제 순서를 부여한다.

v1 또는 v1 명령 접두사가 있는 이전 캠페인은 기존 리뷰 후보 선택을 유지한다. 해당 캠페인의 저장된 리뷰와 명령 replay를 바꾸지 않기 위한 호환 경계이며, P1의 1→2→3 게이트는 네이티브 현재 캠페인에 적용한다. 새 저장 필드나 마이그레이션은 추가하지 않는다.

## 7. 해킹 경로 깊이

`getHackTreeProgress(state, tree)`는 각 탭의 기존 네 노드와 구매 기록에서 다음 값을 계산한다.

- 구매 수 / 전체 수
- 다음 미구매 노드의 이름·비용·효과
- 경로 완성까지 남은 총 구매 비용
- 마지막 노드의 이름·효과

해킹 탭 설명 아래에 `해킹 경로 진척` 영역을 한 번만 둔다. 탭을 바꾸면 같은 영역의 값만 갱신한다.

표시 예:

```text
경로 진척 1/4 · 완성까지 31 RES
다음: 요청 가로채기 · 6 RES — 대상 요청 중 최대 5%p 지속 가로채기
최종: 근원 차단 — 대상 성능 -40, 삭제 임박 시 자비 사건
```

모든 노드를 구매하면 `경로 완성`을 표시한다. 비용·효과·선행 조건은 기존 정의를 그대로 사용하며 밸런스 수치는 바꾸지 않는다.

## 8. 검증

### 자동 검증

- 네 캠페인 단계와 높은 단계 우선순위를 순수 상태 fixture로 검증한다.
- 상단 단계 표시와 `data-campaign-phase`가 같은 결과를 사용하는지 검증한다.
- 첫 차단 사건은 즉시, 대기 사건은 정확히 2초 뒤 표시되는지 fake timer로 검증한다.
- 2초 간격 중 상태가 새 사건으로 바뀌면 이전 타이머가 잘못된 사건을 열지 않는지 검증한다.
- 리뷰 호가 단계를 건너뛰거나 이전 단계로 되돌아가지 않는지 2년 결정론 캠페인과 경계 fixture로 검증한다.
- 각 해킹 탭의 0/4, 중간 진척, 4/4 완료와 다음·최종 효용을 검증한다.
- 저장 round-trip과 replay 결과가 P1 전후 동일한 상태 구조를 유지하는지 기존 전체 검증으로 확인한다.

### 화면 검증

- 1280×720과 1440×900에서 상단 단계 표시와 기존 지표가 겹치지 않는다.
- 해킹 패널에서 첫 비교, 경로 진척, 노드 목록, 확보 리소스가 내부 스크롤 범위 안에 남는다.
- 단계별 강조가 텍스트와 구조를 대신하지 않고 색상만으로 정보를 전달하지 않는다.
- 전체 문서에 가로·세로 스크롤이 생기지 않는다.

## 9. 푸시·머지 게이트

- P1의 기능별 커밋과 최종 `pnpm verify`가 모두 통과한 직후가 푸시 적기다.
- 현재 원격 `origin/agent/permission-zero-demo`는 P0 이전이므로 P0·P1을 함께 푸시한다.
- 사용자 소유 4개 수정이 작업 트리에 남아 있어도 P1 커밋에 포함되지 않았다면 푸시는 안전하다.
- 머지는 원격 CI가 같은 커밋에서 통과하고, 브랜치 diff에 P0·P1 커밋과 의도한 문서만 있는 것을 확인한 뒤 진행한다.
- 대상 브랜치가 `main`이라면 직접 병합보다 PR 검토 후 병합을 기본으로 한다. 충돌이 있으면 대상 브랜치 최신 상태를 이 브랜치에 먼저 반영하고 `pnpm verify`를 다시 실행한다.
