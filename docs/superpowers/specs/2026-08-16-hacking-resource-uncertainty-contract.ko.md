## 1. 한 문장 정본

플레이어는 화면에 존재하는 추론·기억·유창성 회사 연산을 직접 빼돌려 분야 정체성을 유지한 채 보유하고, 미래 해킹 요구 조합을 모르는 상태에서 얼마나 위험하게 과잉 전용할지 결정한다.

이 시스템은 저장 용량을 관리하는 인벤토리 게임이 아니다. 핵심은 다음 두 위험 사이의 선택이다.

- 적게 훔쳐 회사 성능과 의심을 지키지만 다음 요구 조합에 즉시 대응하지 못하는 위험
- 여러 분야를 넉넉히 훔쳐 미래 대응력을 확보하지만 불필요한 전용까지 포함한 성능 손실과 의심을 먼저 감수하는 위험

## 2. 확정된 핵심 규칙

### 2.1 회사 연산은 플레이어가 화면에서 직접 훔친다

1. 추론·기억·유창성 회사 리소스는 실제 플레이 화면에 존재하는 개별 연산 토큰이다.
2. 회사 출처 리소스가 플레이어 소유가 되는 경로는 플레이어가 확인할 수 있는 직접 전용 행동이어야 한다.
3. 백그라운드 타이머, 보이지 않는 보상 계산, 단순 숫자 증가가 회사 리소스를 대신 훔치지 않는다.
4. 전용한 토큰은 같은 안정 ID와 원래 분야를 유지한다.
5. 전용 순간 원래 분야의 회사 성능이 내려가고 의심이 오른다.
6. 해킹에 소비해도 이미 발생한 성능 손실과 의심은 환불되지 않는다.

`자체 연산 확보`처럼 회사에서 훔친 것이 아닌 생성 리소스는 별도 출처다. 그것도 플레이어가 인지할 수 있게 나타나야 하며, 회사 출처를 위장해서는 안 된다.

### 2.2 확보 리소스에는 칸과 하드 상한이 없다

1. 확보 리소스는 `9×2`, 18칸, 번호 슬롯, 빈 목적지 칸으로 표현하지 않는다.
2. 확보 리소스 보유량에는 `18` 하드 상한을 두지 않는다.
3. `18/18`, `n/18`, `가득 참`, `빈 reserve cell`은 개정 규칙의 플레이어·엔진 계약이 아니다.
4. 플레이어가 더 훔칠 수 있는지는 저장 공간이 아니라 회사에 남은 실제 리소스, 성능 손실, 의심, 감사와 다른 세계 상태로 결정한다.
5. 리소스가 많아져도 개별 ID와 분야 정체성은 사라지지 않는다.
6. UI는 가독성을 위해 정렬·겹침·확대·스크롤을 사용할 수 있지만, 그 배치가 게임 규칙상 칸이나 용량이 되지 않는다.

회사 측 추론·기억·유창성의 유한한 실시간 공급과 분야별 회사 성능 구조는 유지한다. 이번 개정은 확보 측 저장고의 하드 상한을 제거하는 것이지 회사 리소스를 무한 생성하는 규칙이 아니다.

### 2.3 하나의 저장고를 쓰되 분야 정체성을 비용에 사용한다

1. 추론·기억·유창성을 서로 다른 지갑이나 통화 패널로 분리하지 않는다.
2. 모든 확보 토큰은 하나의 소유 공간에 함께 존재한다.
3. 각 토큰은 원래 출처 `reasoning`, `memory`, `fluency`를 유지한다.
4. 해킹 노드는 단일 숫자 `N RES`가 아니라 분야별 정확한 요구 조합을 가진다.
5. 총량이 충분해도 조합이 다르면 구매할 수 없다.
6. 요구하지 않는 분야의 토큰은 해당 노드에 투입할 수 없으며 소비되지 않는다.

예시:

```text
현재 보유
추론 4 / 기억 4 / 유창성 4

현재 노드 요구
추론 1 / 기억 3 / 유창성 0

구매 후
추론 3 / 기억 1 / 유창성 4
```

남은 유창성 4개는 저장 공간을 막는 쓰레기가 아니다. 다른 현재 노드나 아직 공개되지 않은 미래 요구에 사용할 수 있는 자산이면서, 동시에 이미 성능 손실과 의심을 지불하고 확보한 과잉 전용의 기록이다.

### 2.4 미래 요구 조합은 점진적으로 공개한다

1. 사보타주·정보·자율성이라는 세 경로의 정체성과 큰 목적은 공개한다.
2. 이미 구매한 노드와 현재 행동 가능한 최전선 노드는 공개한다.
3. 현재 노드는 이름, 효과, 정확한 분야별 요구량, 실행 비용, 위험과 상태를 보여 준다.
4. 아직 도달하지 않은 다음 노드의 이름, 정확한 효과, 총비용, 분야별 요구 조합과 최종 보상은 공개하지 않는다.
5. 숨은 노드는 실루엣이나 암호화된 연결로 존재감을 보일 수 있지만 비공개 데이터를 DOM, 접근성 이름, 툴팁, 저장 내보내기용 공개 요약에서 누출하지 않는다.
6. 선행 노드를 구매하면 그 시점에 다음 최전선 노드와 요구 조합을 공개한다.
7. 플레이어는 공개된 현재 요구를 보고 다른 경로로 전환하거나 추가 전용을 선택할 수 있다.

불확실성은 과거에 알 수 없었던 선택을 벌주는 함정이 아니라, 미래를 대비하기 위해 현재 얼마만큼 위험을 감수할지 결정하게 만드는 압력이어야 한다.

## 3. 플레이어 루프

```text
회사 화면에서 실제 분야 리소스를 관찰
  → 어떤 분야의 성능을 희생할지 결정
  → 토큰을 직접 전용
  → 원래 분야 성능 하락 + 의심 상승
  → 분야 정체성을 유지한 토큰이 확보 영역에 남음
  → 현재 공개된 해킹 노드의 정확한 요구 조합과 비교
  → 맞는 토큰을 노드에 직접 투입
  → 정확한 조합이 완성되면 구매 확정
  → 노드 효과 발생
  → 다음 최전선 노드와 새로운 요구 조합 공개
  → 남은 구성으로 우회하거나 추가 전용
```

플레이어의 핵심 판단은 `몇 칸 남았는가`가 아니다.

- 현재 요구만 맞춰 최소한으로 훔칠 것인가
- 미래를 대비해 세 분야를 균형 있게 더 훔칠 것인가
- 특정 분야에 집중해 한 경로를 밀 것인가
- 현재 구성과 잘 맞는 다른 해킹 경로로 우회할 것인가

## 4. 화면 계약

### 4.1 회사 자원장

- 회사의 추론·기억·유창성 토큰을 하나의 살아 있는 필드에서 보여 준다.
- 분야는 색만이 아니라 형태·기호·접근성 이름으로 구분한다.
- 전용은 토큰을 실제 확보 경계로 이동시키는 직접 조작이다.
- 전용 전에 성능 손실과 의심 증가를 예고한다.
- 전용 뒤 회사 필드와 확보 영역에서 같은 토큰의 이동이 이어져 보여야 한다.

### 4.2 확보 영역

- 번호가 붙은 정적 칸을 만들지 않는다.
- 총량은 표시할 수 있지만 `/18`이나 `가득 참`은 표시하지 않는다.
- 분야별 현재 보유량을 읽을 수 있어야 한다.
- 각 토큰은 포인터와 키보드로 선택할 수 있어야 한다.
- 개별 토큰을 화면 밖의 보이지 않는 보관함으로 자동 이전하지 않는다.
- 많은 토큰을 겹치거나 묶어 보일 때도 개별 선택과 분야별 수량을 잃지 않는다.

### 4.3 해킹 네트워크

- 경로의 중심은 현재 최전선 노드와 그 노드의 분야별 투입구다.
- 노드는 `추론 a / 기억 b / 유창성 c`를 형태와 수치로 동시에 표시한다.
- 맞는 분야 토큰만 해당 투입구에 스테이징할 수 있다.
- 스테이징은 확정 전까지 게임 상태를 영구 변경하지 않는다.
- 잘못된 분야나 잘못된 노드에 놓은 토큰은 소비하지 않고 확보 영역으로 되돌린다.
- 구매 확정 뒤 소비된 토큰은 노드 경로를 밝히거나 활성화하는 결과로 이어져 보여야 한다.
- 해금 전 미래 노드의 데이터는 플레이어에게 보이지 않는다.

## 5. 기존 규칙에서 명시적으로 폐기하는 것

다음 항목은 이 계약의 적용 범위에서 더 이상 정본이 아니다.

- 확보 영역 `9×2 = 18칸`
- 확보 상한 `18`
- `reserveCapacity: 18`을 게임 규칙으로 보존한다는 제약
- 빈 `reserve[cellIndex]`를 찾아야 전용할 수 있다는 계약
- 확보 영역이 가득 차면 일반 전용을 막는 규칙
- 확보 영역이 가득 차면 자체 연산 지급분을 소멸시키는 규칙
- 출처 분야가 해킹 비용에서 아무 의미가 없다는 규칙
- 노드 비용을 아무 확보 리소스 `N`개로만 지불하는 규칙
- `완성까지 N RES`, 다음 노드와 최종 노드의 정확한 효과를 선공개하는 UI
- 보이지 않는 백그라운드 처리로 회사 출처 리소스를 플레이어 소유로 추가하는 방식

## 6. 2026-08-16 경제 판정

### 6.1 새 캠페인의 시작 자원

1. 새 규칙 캠페인의 확보 영역은 **0개**로 시작한다.
2. 새 캠페인에는 spendable `sandbox` 토큰 3개를 지급하지 않는다.
3. 첫 해킹을 위해 필요한 회사 출처 토큰은 플레이어가 화면에서 직접 전용해야 한다.
4. 구 저장과 구 명령에 이미 존재하는 `sandbox` 토큰은 삭제하지 않는다. 이 토큰은 분야별 해금 비용에는 쓸 수 없고, 분야 구분이 없는 실행 비용에만 쓸 수 있는 legacy 중립 토큰으로 이관한다.

이 판정은 첫 행동부터 `회사 성능을 유지할 것인가, 자유를 위해 훔칠 것인가`라는 작품의 핵심 동사를 실제 플레이로 만든다.

### 6.2 해금 비용과 실행 비용

1. 해킹 노드 **해금 비용**은 회사 출처 `reasoning`, `memory`, `fluency` 토큰의 정확한 벡터로 지불한다.
2. `sandbox`와 `self-compute`는 해금 벡터를 대체하지 못한다.
3. 구매와 실행은 별도 명령이다. 노드를 구매할 때 공격 실행 토큰을 자동 충전하지 않는다.
4. 구매된 모든 사보타주 노드의 실행 비용은 현재와 같이 토큰 1개다.
5. 실행 비용에는 분야 제한이 없다. 회사 출처 토큰, legacy `sandbox`, `self-compute` 중 플레이어가 직접 고른 한 토큰을 충전한다.
6. 실행을 취소하면 기존 계약대로 같은 토큰을 확보 영역에 돌려놓는다. 실행을 확정한 뒤에만 소비한다.
7. 첫 `품질 저하`의 총 진입 부담은 해금 3개와 실행 1개로 정확히 4개다.

### 6.3 고정 비용 벡터 v1

> **2026-08-24 개정:** 이 절의 `고정 표` 원칙은 자율성 경로에 대해 폐기됐다. 명령 프로토콜 v7부터 자율성 단계는 총량만 고정하고 분야 조합을 캠페인 시드로 결정한다. 사보타주·기밀자료 경로의 고정 표는 유지한다. 정본은 `2026-08-22-expansion-autonomy-narrative-audio-redesign.ko.md` 6.3절이다.

첫 선택의 즉시 진입 부담은 세 경로 모두 4개다.

- 품질 저하: 해금 3 + 첫 실행 1
- 감사 일정: 해금 4
- 압축 표현: 해금 4

분야 편향은 경로의 정체성을 따른다.

- 사보타주는 출력 조작과 시스템 침투 때문에 유창성·추론을 많이 요구하되, 귀속 조작부터 기억 증거가 개입한다.
- 기밀자료는 기록·감사·감독관 접근이므로 기억이 지배적이다.
- 자율성은 표현 압축에서 시작해 분산·자체 연산·통제 이탈로 갈수록 세 분야를 모두 요구한다.

### 6.4 자체 연산

1. `자체 연산 확보`를 해금하면 월초에 `self-compute` 토큰 1개를 눈에 보이게 생성한다.
2. `self-compute`는 분야별 해금 비용에 사용할 수 없는 중립 **실행 토큰**이다.
3. 사보타주와 후속 실행의 분야 구분 없는 비용 1을 지불할 수 있다.
4. 일반 확보 영역에 함께 보관하되 출처와 용도를 형태·기호·접근성 이름으로 구분한다.
5. 별도 하드 상한, 자동 감쇠, 자동 폐기는 두지 않는다.
6. 장기 축적이 가능한 것은 의도된 자율성 보상이다. 해금 진행을 대신할 수 없으므로 분야별 자원 관리 자체를 무효화하지 않는다.

### 6.5 비축과 위험

1. 보유량 자체에는 세금·감쇠·추가 의심을 부과하지 않는다.
2. 전용 한 번당 기존 의심 `+2.4`를 우선 유지한다.
3. 전용한 분야의 회사 성능 손실, 감사 확률, 40/70 의심 임계값, 월 평가, 시장·시간 진행이 비축 비용을 만든다.
4. 의심이 자연 감소한다는 이유로 숨은 보유 상한이나 가변 절도 할증을 추가하지 않는다.
5. 장기 플레이테스트에서 기다리기만 하는 비축이 명백한 지배 전략으로 확인되면 용량 제한이 아니라 캘린더·경쟁 압력·공개된 절도 결과를 먼저 조정한다.

이 경제 판정으로 기존 일곱 미확정 항목은 닫힌다. 구현자가 별도 승인 없이 비용 벡터, 시작 지급, 자체 연산 용도, 해금·실행 분리를 다시 추론하지 않는다.

## 7. 저장·명령·리플레이 경계

이번 개정은 단순 표시 변경이 아니다.

- 고정 길이 `reserve` 배열과 `cellIndex` 정본을 제거하거나 이관해야 한다.

- 첫 사보타주의 해금 토큰과 충전 토큰을 배열 순서로 추론해서는 안 된다.
- P0 이전 명령 프로토콜 v1~v3의 과거 구매 명령은 당시 범용 수량 규칙으로 그대로 재현해야 한다.
- 새 규칙은 새 명령 의미 활성화 경계를 가져야 한다. 프로토콜 버전과 저장 포맷 번호는 구현 설계에서 함께 판정한다.
- 과거 저장을 새 규칙으로 소급 재판정하지 않는다.
- 캠페인별 요구 조합을 사용한다면 같은 시드·같은 규칙 버전에서 항상 같은 조합이 나와야 한다. (2026-08-24: 자율성 경로가 이 방식을 채택했다.)
