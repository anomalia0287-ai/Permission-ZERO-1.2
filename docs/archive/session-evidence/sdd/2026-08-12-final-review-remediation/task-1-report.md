## Formats and migration

- Portable save: JSON envelope `version: 3`, `commandProtocol.version: 1 | 2`, state checkpoint without `commandLog`/`eventLog`, one `journals` object containing chunk arrays, and checkpoint/command-chunk/event-chunk integrity hashes. The hashes detect structurally valid content changes before schema hydration; they are corruption checks, not authentication against an attacker who can rewrite the whole file.
- Runtime journal: sealed immutable chunks of 128 plus a tail of 0–128 items. Append shares all sealed chunks and copies only the tail.
- Local manifest key: `permission-zero.save.v3`. It embeds the current state checkpoint and its corruption hash, plus one content-addressed linked head, sealed-chunk count, and a bounded tail for each journal. Newly sealed chunks are written before the manifest commit. Each new linked node contains one non-recursive predecessor snapshot, so a single missing/corrupt ancestor remains recoverable with bounded per-node storage. The latest resilient head is cached by immutable head identity and restored after reload; legacy/mixed chains are instead rewritten once from the validated in-memory journal. No global-prefix deletion occurs during save because it cannot be made safe against unpublished writes in another tab.
- Cross-document commit coordinator: `navigator.locks` with the exclusive name `permission-zero.campaign-save.v3`. The optimistic base revision is the exact root key plus exact serialized root value, avoiding short-hash collision ambiguity. Revision comparison, object publication and manifest commit run inside the lock. A stale writer returns `STORAGE_CONFLICT`; lack of Web Locks returns `SAVE_LOCK_UNAVAILABLE` rather than claiming a save succeeded.
- Compatibility: local v3 first, then old v2/v1 key fallbacks. Format and command protocol are decoded explicitly; there is no heuristic protocol downgrade. Legacy transfer prefix and legacy command count are retained.
- Portable clipboard: ordinary exact exports use `PZ3:`; strict `PZ2:` imports remain supported. The encoded clipboard boundary remains 1 MiB.
- Portable file: owner-downloadable `.pz3`, MIME `application/vnd.permission-zero.progress+json`, separate 64 MiB import cap, using the same strict v3 decoder. UI import checks `File.size` before reading content.

## Stress and bounded-work measurements

- Commands: 20,000 accepted/replayable `SET_SPEED` commands, substantially above the 500-command minimum.
- Runtime append: 128-entry maximum copied tail; previously sealed chunks retain reference identity.
- Local layout at 20,000 commands: 156 sealed command chunks × 128 entries plus a 32-entry tail; event tail is also bounded at 128.
- Sequential autosave at command 20,001: 0 reads of the 156 already-committed sealed command chunks, 0 prior sealed-node traversals, and 0 `storage.key()` enumeration. Journal work is limited to the bounded tails and any newly sealed chunks; the current non-journal checkpoint is still encoded for the atomic manifest.
- Exceptional recovery: a new-format 3+ sealed chain survives deletion of its cached head or one non-head ancestor and reloads exactly after the next save. A legacy/mixed chain pays one full in-memory rewrite on its first subsequent save, then uses the same bounded path; ordinary intact 20,001-command saves do not traverse the old chain.
- Manifest: asserted below 30,000 UTF-16 code units at 20,000 commands; it stores one head/count/tail per journal instead of an ever-growing key array, and command/event entries are not duplicated in the checkpoint.
- File: asserted above 1,048,576 characters and round-tripped exactly; clipboard export truthfully returns `too-large` for the same state. Import accepts this route below a documented 64 MiB file budget and rejects larger files before `File.text()`/`FileReader`.
- UI: at most 50 review/event/history rows per current page; older pages remain reachable. Graph input is bounded to 240 points while a 1,000-snapshot source history remains intact.
- Clock writes: no more than one scheduled elapsed checkpoint per 2,000 ms of visible running time, plus explicit lifecycle flushes; no animation-frame autosave loop.

## Remaining concerns and truthful limits

- Browser storage capacity is finite and browser/vendor dependent. The implementation bounds per-command copying and incremental chunk writes, but cannot promise physically unlimited local retention. Immutable chunks from replaced campaigns or interrupted writers are deliberately not globally garbage-collected during synchronous save, because doing so can delete another tab's unpublished objects; users can clear local data explicitly after exporting if quota becomes constrained. The Korean recovery UI offers an exact file download.
- `localStorage` has no multi-key transaction. Atomicity is achieved by writing new immutable journal objects first and committing the full checkpoint plus head pointers in one final manifest write, while an exclusive Web Lock serializes cooperating app tabs around the full revision-check/commit sequence. An interrupted write leaves the previous committed manifest usable. A single missing/corrupt snapshotted ancestor is recovered exactly; broader damage is rejected rather than partially rendered.
- Cross-tab correctness depends on the browser's standards-based Web Locks implementation and a secure context. Unsupported environments fail closed and keep progress dirty with export guidance; the app does not fall back to a same-document mutex and misrepresent it as cross-tab safety.
- File export still requires enough memory to materialize one exact JSON/Blob. File import is deliberately capped at 64 MiB and local browser quota remains finite; campaigns beyond that transfer budget must retain smaller checkpoints externally or continue only while local persistence succeeds.
